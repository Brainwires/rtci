# Packaging: the C interface, bindings and release artefacts

The engine is a Rust library. `rtc-ffi` makes it usable from any language with a C FFI (C,
C++, Deno, Node, Python, Go, Swift, ...) and installable without a Rust toolchain, as prebuilt
libraries. This page is its reference: the two layers of the interface, the memory and thread
rules, building for each platform, the Deno example, what a release would contain, and the
two decisions left to the owner.

## The crate

`rtc-ffi/` is a workspace member built as `cdylib` (`librtc_ffi.so`, `librtc_ffi.dylib`,
`rtc_ffi.dll` with `rtc_ffi.dll.lib`), `staticlib` (`librtc_ffi.a`, `rtc_ffi.lib`) and `rlib`.
Its header is `rtc-ffi/include/rtc.h`, generated by [cbindgen](https://github.com/mozilla/cbindgen)
from the crate's source and checked in; the `C header up to date` job of `cargo.yml`
regenerates it and fails on a difference. cbindgen (MPL-2.0) is a build tool run in CI only,
not a dependency of any crate. After changing the interface:

```sh
cargo install cbindgen --locked --version 0.29.2
cbindgen --config rtc-ffi/cbindgen.toml --crate rtc-ffi --output rtc-ffi/include/rtc.h
```

Feature `driver` (default) adds the driven layer; without it (`--no-default-features`) the
library has the sans-I/O layer only, and a C user defines `RTC_FFI_NO_DRIVER` before including
the header.

## Rules of the boundary

| Rule | How |
|---|---|
| Status codes | Every function returns `int32_t`: `RTC_OK` (0), `RTC_EMPTY` (1: nothing to poll, no value), or a negative `RTC_ERR_*`: `INVALID_ARGUMENT`, `BUFFER_TOO_SMALL`, `ENGINE` (the engine refused: W3C errors, malformed SDP), `JSON`, `PANIC`, `NOT_FOUND`, `IO`, `CLOSED`. |
| Error text | `rtc_last_error(buf, cap)` copies the calling thread's last error message (kept until the next error on that thread) and returns its length. |
| No panic crosses | Every entry point catches unwinding and returns `RTC_ERR_PANIC`; a `rtc_pc` whose call panicked is poisoned and refuses later calls (`RTC_ERR_CLOSED`) except its free. |
| Allocations | Every handle has a `_free` (`rtc_pc_free`, `rtc_driven_free`, `rtc_mux_free`); every string returned through `char **out` is freed with `rtc_string_free`. Strings passed in are borrowed for the call. `rtc_debug_live_objects()` counts handles and strings not yet freed (the tests' leak check). |
| Caller buffers | `poll_*` and `rtc_driven_next` write into the caller's buffer; one too small gives `RTC_ERR_BUFFER_TOO_SMALL` with the length needed and keeps the item for the retry. |
| JSON | Configuration, settings, inits, events, stream commands, statistics and object info are JSON with the W3C member names; unknown members are refused (`RTC_ERR_JSON`), so a binding learns of a typo or of a member this version lacks. |
| Time | The caller passes monotonic nanoseconds (`now_ns`) on an origin of its own (0 for a virtual clock, `CLOCK_MONOTONIC`, `performance.now() * 1e6`); they must not go backwards for one connection. Deadlines come back in the same nanoseconds. The engine takes wall-clock time (RTCP sender reports, statistics timestamps) from the system clock itself, paired with the caller's time; no engine entry point takes a wall-clock reading, so the interface has none. |
| Symbols | Every export starts with `rtc_`. `rtc_abi_version()` (now 1) changes with any signature, struct layout or status meaning; a binding checks it at load. `rtc_version()` is the crate version. |

Thread safety: a `rtc_pc` is not thread-safe (calls must not overlap; it may move between
threads between calls). A `rtc_driven` and a `rtc_mux` are thread-safe, except that their free
must not overlap another call on them, and that the driven layer's callback runs on its own
thread, from which `rtc_driven_call` is refused.

## Layer 1: sans-I/O (`rtc_pc_*`)

The Rust API one to one. The caller owns the sockets and the clock and runs the loop of the
README's "Driving the Engine".

| Group | Functions |
|---|---|
| Lifetime | `rtc_pc_new(configuration_json, settings_json, now_ns, &pc)`, `rtc_pc_free`, `rtc_pc_close` |
| Signaling | `rtc_pc_create_offer`, `rtc_pc_create_answer` (options JSON), `rtc_pc_set_local_description`, `rtc_pc_set_remote_description` (`{"type","sdp"}`), `rtc_pc_description` (local / current / pending, remote ...), `rtc_pc_add_local_candidate`, `rtc_pc_add_remote_candidate` (`RTCIceCandidateInit`), `rtc_pc_restart_ice`, `rtc_pc_set_configuration`, `rtc_pc_states`, `rtc_pc_ice_username_fragments` |
| Data channels | `rtc_pc_create_data_channel(label, init_json, &id)`, `rtc_pc_data_channel_send`, `_close`, `_info`, `_set_buffered_amount_low_threshold` |
| Media | `rtc_pc_add_track(track_json, &sender)`, `rtc_pc_remove_track`, `rtc_pc_add_transceiver(kind, init_json, &id)`, `rtc_pc_transceivers`, `rtc_pc_transceiver_set_direction`, `_stop`, `rtc_pc_sender_info`, `rtc_pc_receiver_info`, `rtc_pc_sender_write_rtp` (a packet), `rtc_pc_sender_write_frame` (an encoded frame, packetized with the negotiated codec) |
| Event loop | `rtc_pc_handle_read(now, &rtc_transport, data, len)`, `rtc_pc_poll_write(&rtc_transport, buf, cap, &len)`, `rtc_pc_poll_read(&rtc_message, buf, cap)` (RTP / RTCP in wire form, data channel messages), `rtc_pc_poll_event(buf, cap, &len)` (JSON), `rtc_pc_poll_timeout(&ns)`, `rtc_pc_handle_timeout(now)` |
| Streams (ICE-TCP, TURN over TCP / TLS) | `rtc_pc_poll_stream_command` (JSON), `rtc_pc_poll_stream_transmit`, `rtc_pc_handle_stream_event` (JSON), `rtc_pc_handle_stream_accepted`, `rtc_pc_handle_stream_read` |
| Statistics | `rtc_pc_get_stats(now, selector, id, &json)`: the report as an object keyed by stats id |

`configuration_json` is a W3C `RTCConfiguration` (`iceServers`, `iceTransportPolicy`,
`bundlePolicy`, `rtcpMuxPolicy`, `iceCandidatePoolSize`). `settings_json` holds the engine
settings a binding needs (`iceLite`, `nat1to1Ips`, `nat1to1CandidateType`,
`answeringDtlsRole`, `tcpCandidateGathering`, `iceCredentials`, `iceTimeouts`,
`disableCertificateFingerprintVerification`, `interceptors`: `"default"` or `"minimal"`).
Events are `{"type": <W3C event name>, ...}` (`icecandidate`, `connectionstatechange`,
`datachannel`, `open`, `close`, `track`, `negotiationneeded`, ...); the ones without a W3C
name keep a name of this interface, and one this version does not know is
`{"type": "other", "debug": ...}`.

## Layer 2: driven (`rtc_driven_*`, `rtc_mux_*`, feature `driver`)

A browser-like object that owns its sockets and a thread: the reference tokio driver
(`examples/stream-driver`) embedded.

- `rtc_driven_new(configuration_json, settings_json, options_json, mux, &d)` binds the
  sockets and gives the engine its host candidates before it returns. The options are the
  server choices: `bindAddresses`, `includeLoopback`, `includeLinkLocal`, `portRange`
  `{min, max}` (UDP sockets and ICE-TCP listeners), `tcp` (the engine's ICE-TCP and TURN over
  TCP / TLS; on by default), `natIps` / `natCandidateType` (1:1 NAT), `iceLite`.
- `rtc_driven_call(d, method, params_json, data, len, &out_json)` runs one operation on the
  thread: the same operations as layer 1, by name (`createOffer`, `setLocalDescription`,
  `addIceCandidate`, `createDataChannel`, `dataChannelSend`, `addTrack`, `addTransceiver`,
  `writeFrame`, `writeRtp`, `getStats`, `localAddresses`, `close`, ...; the list is in the
  header). They are carried out by layer 1's own entry points.
- What happens comes as items, a JSON header and a payload: every event of layer 1,
  `message` (a data channel message), `rtp` / `rtcp` (a packet), `error`, and a last
  `closed`. Either a callback receives them on the thread (`rtc_driven_set_callback`), or they
  queue: `rtc_driven_wait(d, timeout_ms)` blocks until one is there (declare it `nonblocking`
  in Deno), `rtc_driven_next(d, buf, cap, &json_len, &data_len)` takes one.
- `rtc_driven_close` closes the connection (the remote is told), stops the thread and closes
  the sockets; `rtc_driven_free` does the same and frees the handle.
- `rtc_mux_new({"udp": "ip:port", "tcp": "ip:port"})` opens one UDP port and optionally one
  passive ICE-TCP port shared by every driven connection created with it, routed by the ICE
  ufrag of the first check (`UfragMux`, `accept_by_ufrag`). It binds a concrete address
  (candidates carry it). `rtc_mux_addresses`, `rtc_mux_free` (after its connections).

The driven layer gathers host candidates for the default transport (BUNDLE); sections a
remote keeps out of a BUNDLE group get no socket of their own. mDNS is not served.

## Building for each platform

```sh
cargo build -p rtc-ffi --release                 # this machine; target/release/
cargo build -p rtc-ffi --release --no-default-features   # the sans-I/O layer only
```

| Platform | Command | Output | Notes |
|---|---|---|---|
| Linux x86_64 / aarch64, glibc 2.17+ | `cargo zigbuild -p rtc-ffi --release --target x86_64-unknown-linux-gnu.2.17` (or `aarch64-...`) | `librtc_ffi.so`, `librtc_ffi.a` | [cargo-zigbuild](https://github.com/rust-cross/cargo-zigbuild) (MIT) with Zig (MIT) links against a glibc 2.17 sysroot. Link the static library with `-lpthread -ldl -lm -lrt -lutil`. |
| macOS aarch64 / x86_64 | `MACOSX_DEPLOYMENT_TARGET=11.0 cargo build -p rtc-ffi --release --target aarch64-apple-darwin` (`10.13`, `x86_64-apple-darwin`) | `librtc_ffi.dylib`, `librtc_ffi.a` | Both build on an Apple-silicon host. |
| Windows x86_64 (MSVC) | `cargo build -p rtc-ffi --release --target x86_64-pc-windows-msvc` | `rtc_ffi.dll`, `rtc_ffi.dll.lib`, `rtc_ffi.lib` | Link the static library with `ws2_32 userenv ntdll bcrypt advapi32 kernel32 iphlpapi`. |

The crypto provider is ring (C and assembly, built by its build script with the platform's C
compiler); no system library is needed at run time beyond libc.

## Tests

- `rtc-ffi/tests/sans_io.rs`: two peer connections that see each other only through the C
  declarations (`tests/abi/mod.rs`), on a virtual clock: a data channel echo of a string and
  a binary message, Opus RTP both ways (packets one way, frames the other) with `getStats`,
  renegotiation adding a video transceiver to a connected pair, close, error codes and
  buffer retries. `sans_io_leaks.rs`: a whole session leaves no live object.
- `rtc-ffi/tests/driven.rs`: two driven connections over loopback, one on a shared UDP and
  TCP port, one delivering to a callback: a data channel message and Opus frames, statistics,
  port ranges, the leak check.
- `rtc-ffi/tests/c_loopback.rs`: compiles `tests/c/loopback.c` against the static library and
  the header with the platform's C compiler (the `cc` crate) and runs it: a C program's data
  channel echo through the driven layer, then the leak check. `cargo test` builds the library
  as an rlib only, so the test builds the static library with a nested `cargo build` in a
  target directory of its own (under `target/tmp`); the link flags per platform are those of
  the table above.

## The Deno example

`bindings/deno/mod.ts` is the browser API (`RTCPeerConnection`, `RTCDataChannel`,
`RTCRtpTransceiver` / `Sender` / `Receiver`, `RTCSessionDescription`, `RTCIceCandidate`,
events, `getStats`) over the driven layer with `Deno.dlopen`, the server options as the second
constructor argument, `RTCSharedPort` for the mux, and encoded media (`writeFrame`,
`writeRtp`, the receiver's `rtp` event). It loads `RTC_FFI_LIB`, else the library beside the
module; it downloads nothing. It is a reference only: the Denext project maintains its own
binding. See [bindings/deno/README.md](../bindings/deno/README.md).

## What a release would contain

`.github/workflows/release-binaries.yml` runs only by hand (`workflow_dispatch`; never on a tag,
branch or pull request, until the owner decides how release binaries are built) and builds, on GitHub's runners:

| Archive | Target | Baseline |
|---|---|---|
| `rtc-ffi-<tag>-linux-x86_64.tar.gz` | `x86_64-unknown-linux-gnu` | glibc 2.17 (checked: no newer symbol version) |
| `rtc-ffi-<tag>-linux-aarch64.tar.gz` | `aarch64-unknown-linux-gnu` | glibc 2.17 |
| `rtc-ffi-<tag>-macos-aarch64.tar.gz` | `aarch64-apple-darwin` | macOS 11.0 |
| `rtc-ffi-<tag>-macos-x86_64.tar.gz` | `x86_64-apple-darwin` | macOS 10.13 |
| `rtc-ffi-<tag>-windows-x86_64.tar.gz` | `x86_64-pc-windows-msvc` | Windows 10, MSVC |

Each archive holds `lib/` (the shared and the static library), `include/rtc.h`, the two
licence files and `build.json` (target, baseline, commit). Beside them: `SHA256SUMS` and
`manifest.json` (ref, commit, ABI version, and per archive its target, baseline, SHA-256 and
size), which a loader like Deno's can use to pick and verify a download. A dispatch uploads
everything as workflow artifacts; a dispatch on a tag ref also attaches it to the GitHub release
of that tag. The workflow takes no secret but `GITHUB_TOKEN` and has not been run.

## Decisions left to the owner

1. **Tagging and publishing.** Nothing here tags, creates a release or publishes to a registry
   (crates.io, npm, JSR). A `v*` tag runs `release.yml` only; `release-binaries.yml` is started
   by hand, and how and where release binaries are built (runners, artefacts, signing) is not
   decided yet. Whether and when to tag is the owner's call, as is publishing a Deno or
   other binding anywhere.
2. **Crate names.** On crates.io, the names of upstream's crates belong to webrtc-rs; the
   release renames this project's crates to their `rtci` names (`scripts/rename-to-rtci.py`,
   run as the release's last content commit, `docs/rename.md`). `rtc-ffi` stays `publish = false`: it is delivered as built
   libraries and a header, not as a Rust dependency.

Where the RFC and browsers differ the default is the RFC and the browsers' behaviour is a
setting: upper-case
fingerprint hex only (`with_lowercase_fingerprints_accepted`), `a=tls-id` written
(`with_disable_sdp_tls_id`). The exception is `use_srtp` only with media
(`with_dtls_use_srtp_on_every_association(false)`): browsers do not act on the new `tls-id` it
needs when media is added to a data-channel-only session, so the browsers' form is the default
(train round 8). A sha-1 fingerprint is accepted when the peer offers nothing
stronger, as RFC 8122 defines it, and never produced. As the DTLS server the engine takes an SRTP
profile whenever the client offers one.

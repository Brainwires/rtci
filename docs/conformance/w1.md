### Decisions

| Clause | What the engine does |
|---|---|
| RFC 8841 9.3, closing an association that signalling replaces or closes | An ABORT, not the SHUTDOWN handshake: the new association does not wait for the old one, and messages still queued on the old one are dropped with it. |
| RFC 8841 10.5, a DTLS association replaced under a live SCTP association | The SCTP association is kept: a DTLS handshake that completes again starts no new one. |
| RFC 8831 6.6, deprecated PPID-based fragmentation (PPIDs 52 and 54) | Not reassembled: such a message closes the channel, as any unsupported PPID does. |
| RFC 8831 6.6, the 16 KB limit without interleaving | Applied by default, although no browser applies it and none announces interleaving: an application that sends more than 16 KB at a time to a browser lifts it (`with_sctp_message_size_limit_without_interleaving(false)`), as the browser interop peer does. A refused send gets `ErrMessageTooLargeWithoutInterleaving`, whose text names the limit and `with_sctp_message_size_limit_without_interleaving(false)`. |
| RFC 9260 8.2, an inactive path | Not surfaced: an `RTCSctpTransport` has no state for it, and the association has no other path to use. |
| RFC 6525, the re-configuration requests beyond the outgoing stream reset | Never made by a peer connection (an SSN/TSN reset suspends sending until it is answered); those the peer makes are performed by `rtci-sctp`. |
| RFC 8832 7, a bound on channels the peer opens | None below the negotiated stream count: each channel costs a registry entry and its statistics, freed when it closes. |

# RFC 6062 (TURN extensions for TCP allocations), client role: clause-level audit

Spec: RFC 6062, "Traversal Using Relays around NAT (TURN) Extensions for TCP Allocations",
November 2010. It extends RFC 5766; RFC 8656 (which obsoletes RFC 5766) leaves it in force and
still says REQUESTED-TRANSPORT "is always UDP" for its own allocations.
Audited: fork master 8916bc3, `rtc-turn/`, `rtc-stun/` (constants), `rtc-ice/`, `src/`.
Sections done: all (4 client, 5 server, 6 code points, 7 security).

Result in one line: **not implemented.** `docs/conformance.md` lists "TCP allocations (RFC 6062)"
under "Not implemented, on purpose"; every client clause below is `missing` and counted.

What exists, checked by search for `Connect`, `ConnectionBind`, `ConnectionAttempt`,
`CONNECTION-ID`, `6062` across `rtc-turn`, `rtc-stun`, `rtc-ice` and `src`:

- Code points only: `METHOD_CONNECT` 0x000a, `METHOD_CONNECTION_BIND` 0x000b,
  `METHOD_CONNECTION_ATTEMPT` 0x000c (`rtc-stun/src/message.rs:590-595`, names at `:610-613`),
  `ATTR_CONNECTION_ID` 0x002a (`rtc-stun/src/attributes.rs:187-189`), `CODE_CONN_ALREADY_EXISTS`
  446 and `CODE_CONN_TIMEOUT_OR_FAILURE` 447 (`rtc-stun/src/error_code.rs:150-155`), `PROTO_TCP`
  (`rtc-turn/src/proto/mod.rs:50`). Nothing reads or writes them.
- The client always asks for a UDP relay, also when it reaches the server over TCP
  (`rtc-turn/src/client/mod.rs:715-720,786-791`, test
  `test_allocate_over_tcp_requests_a_udp_relay`), and says so in a comment.
- `Client::handle_stun_message` ignores every indication but Data
  (`rtc-turn/src/client/mod.rs:330-355`), so a ConnectionAttempt would be dropped, and its
  response `match` has no arm for Connect or ConnectionBind (`:379-449`).
- There is no CONNECTION-ID getter / setter, no notion of a control connection versus data
  connections, and no event to ask the application for a second TCP connection.
- Wrong label, not a feature: `rtc-turn/examples/turn_client_tcp.rs:29` describes itself as "TURN
  Client over TCP (RFC 6062)". It is a UDP allocation reached over TCP (RFC 8656 §3.1), not a TCP
  allocation. The label should lose the RFC number.

Level `DESC` marks behaviour stated without an RFC 2119 keyword. Server-only clauses are grouped.

## Gaps, in order of importance

One feature, all of it missing. Whether it is wanted at all is the owner's call: WebRTC does not
use TCP allocations (browsers gather UDP relay candidates only, and ICE-TCP through a relay is not
part of RFC 8839 practice), and RFC 8656 defines only UDP relays. If the goal is "all of the
listed RFCs", these are the work packages:

1. **CONNECTION-ID codec and message plumbing (S).** RFC6062-6.1-1, 6.2-1, 6.3-1, 4.3-3. A
   `ConnectionId(u32)` getter / setter in `rtc-turn/src/proto`, with tests and a fuzz corpus
   entry.
2. **TCP allocation on a control connection (M).** RFC6062-4.1-1 to 4.1-6, 4.2-1, 4.6-1. An
   allocate option for `REQUESTED-TRANSPORT = TCP`, refused when the client's transport is UDP and
   when DONT-FRAGMENT / EVEN-PORT / RESERVATION-TOKEN are set; relay state marked TCP so
   `send_to`, ChannelBind and Send indications are refused on it; refresh as today.
3. **Outgoing connections (M).** RFC6062-4.3-1, 4.3-2, 4.3-10 to 4.3-13. `Relay::connect(peer)`
   sending Connect, one outstanding per peer address, a 10 s hold after 447, an event carrying
   the CONNECTION-ID.
4. **Data connections (L).** RFC6062-4.3-4 to 4.3-9, 4.4-1 to 4.4-6, 4.5-1, 4.6-2. The sans-I/O
   shape is the hard part: an event that asks the application to open another TCP (or TLS)
   connection to the server from a new local port, a per-connection client object that
   authenticates (401, nonce, long-term key shared with the control connection) and sends
   ConnectionBind, then switches that connection to raw pass-through; ConnectionAttempt
   indications surfaced as events with accept / ignore; the 30 s server window.
5. **ICE integration (L, optional).** A relay candidate with transport TCP in `rtc-ice` and the
   peer connection, should relayed ICE-TCP ever be wanted. Nothing in RFC 6062 requires it.
6. **Environment test (M).** coturn supports RFC 6062; a `testenv_turn_tcp_alloc.rs` with two
   clients, one connecting and one accepting, would prove packages 2 to 4.

Size of the whole: L to XL.

## Bugs found

None in behaviour: nothing of RFC 6062 runs. One wrong claim to fix:

1. `rtc-turn/examples/turn_client_tcp.rs:29` names RFC 6062 for an example that makes a UDP
   allocation over a TCP connection to the server. Reproduction: read the Allocate the example
   sends (`REQUESTED-TRANSPORT` is 17). Fix: say "TURN over TCP (RFC 8656 §3.1)".

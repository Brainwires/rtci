# RFC 8627: RTP Payload Format for Flexible Forward Error Correction (FEC)

Spec: RFC 8627, July 2019 (Standards Track). Audited at fork master 8916bc3. Sections covered: 1.1.2,
1.1.7, 1.1.8, 4, 5, 6, 7, 8, 9 (all sections with requirements on an endpoint).

**Status of the implementation.** Implemented on branch `conf/cc-fec-flexfec` as its own coder,
`rtc-interceptor/src/flexfec/rfc8627/` (`FlexFecEncoder`, `FlexFecDecoder`, `FlexFecSendInterceptor`,
`FlexFecReceiveInterceptor`, `FlexFecHeader`, `FlexFecParameters`), selected by `video/flexfec` exactly as
`video/flexfec-03` selects the draft-03 coder (`StreamInfo::mime_type_fec`, `rtp_codec.rs`
`find_fec_format`). The interceptors are opt-in, like the draft-03 pair, and `video/flexfec` is not in
`register_default_codecs`. The draft-03 coder is audited separately in
[draft-ietf-payload-flexible-fec-scheme-03.md](draft-ietf-payload-flexible-fec-scheme-03.md).

The table was written when nothing implemented the RFC, so the Note column of a row this branch did
not change still says what the draft-03 coder does for the same clause: **same**, **differs** or
**neither**.

Where the two wire formats differ (the reason a draft-03 round trip proves nothing about RFC 8627):

| Field | draft-03 (`flexfec-03`) | RFC 8627 (`flexfec`) |
|---|---|---|
| Protected SSRCs | `SSRCCount` + 24 reserved bits + `SSRC_i` words inside the FEC header | CSRC count and CSRC list of the repair packet's RTP header |
| Fixed FEC header before the first mask | 20 bytes | 12 bytes |
| k bit | 1 = this is the last mask (libwebrtc reading) | 1 = another mask follows, 0 = last |
| Third mask | k bit + 63 bits (packets 46..108, 109 in all) | 64 bits, no k bit (packets 46..109, 110 in all) |
| R=1 | F=1: retransmission, parsed differently | R=1 F=0: retransmission; R=1 F=1 reserved |
| F=1 | M / N offsets | L (columns) / D (rows), with defined 1-D and 2-D meanings |
| Subtype | `flexfec-03` in practice | `flexfec` |

## Gaps, in order of importance

Gaps 1 and 2 of the audit (the coder itself; F=1, R=1 and several SSRCs on receive) are closed on
`conf/cc-fec-flexfec`. What remains:

1. **The protected image under transport-wide CC (S).** RFC8627-4.1-1: `Slot::FecEncoder` still runs before
   `TwccSenderInterceptor` writes its header extension. Same slot and same fix as draft-03 Bug 1; it is in
   the congestion-control PR, which also lets repair packets reach the arrival recorders.
2. **`repair-window` in negotiation (M).** RFC8627-5.1-3, 5.2.1-1: the engine does not write the parameter
   (the application's codec registration does) and does not refuse an offer whose window it cannot support;
   the receive interceptor declines to bind such a stream, the answer still carries the payload type.
3. **Repair stream as an RTP source (M).** RFC8627-4.2.1-11, -13 (and -10 untested): SR/SDES CNAME for the
   repair SSRC, SSRC collision handling (shared with draft-03).
4. **Negotiation rules (S, decision).** RFC8627-1.1.7-1 (answer FlexFEC only when offered with RTX:
   libwebrtc does not, left as is for the owner to decide), RFC8627-5.2.1-2 (answer fmtp echoes the offer:
   shared root cause, RFC 7587 audit gap 1), RFC8627-7-2 (in-band SSRC mapping reaches the interceptor only
   when the application routes the undeclared repair SSRC itself).
5. **Adaptive protection (M).** RFC8627-8-3 partly done: the amount follows the reported loss (`FecRate`,
   shared with draft-03 and ULPFEC). Open: choosing the shape (row, column, both) from the burst
   length (8-3), and raising FEC only after the source rate came down (8-2, MAY): today the FEC bit
   rate comes out of the media target at the same time.
6. **Other media types (S).** RFC8627-5.1-4: the engine binds `video/flexfec` only.

## Bugs found

None in the RFC 8627 coder as delivered. The hazard the audit recorded is reduced, not gone: an
application that registers `MIME_TYPE_FLEX_FEC` and no `FlexFecReceiveInterceptor` still gets
`video/flexfec` answered with nothing decoding it (RFC8627-5.2.1-1). The defects of the draft-03 coder are
listed in the draft-03 audit.

# RFC 2198: RTP Payload for Redundant Audio Data (RED)

Spec: RFC 2198, September 1997 (Standards Track; updated by RFC 6354). Audited at fork master 8916bc3.
Whole document covered (sections 3 to 6; 1, 2 and 7 carry no requirement). The RFC predates consistent
RFC 2119 capitalisation in places: lower-case "shall" / "must" that define the format are listed as MUST,
"should" as SHOULD.

**Status of the implementation.** (Branch `conf/cc-fec-ulpfec`: the block header reader and writer now exist
privately in `rtc-interceptor/src/ulpfec/red.rs`, as the carrier of ULPFEC for video, RFC 5109 section 14.2; rows
3-2 to 3-5 and 5-4 are `partial` for that reason. The rest of this paragraph is the state of the general codec.)
RED is not implemented: `docs/conformance.md` decision D1 says so. There
is no packetizer, no depacketizer, no interceptor and no MIME constant for `red`. The only code that knows
the name is the repair-format classifier (`is_repair_codec` / `repair_family`,
`src/rtp_transceiver/rtp_sender/rtp_codec.rs:312-336`), which keeps an application-registered `audio/red`
or `video/red` in codec preferences. An application can therefore register `red`, negotiate it, send RED
packets it built itself (`RTCRtpSender::write_rtp` accepts any negotiated payload type,
`rtp_sender/mod.rs:449-451`) and receive RED packets undecoded on the track. Every format clause is
`missing` for the engine.

## Gaps, in order of importance

1. **RED packetizer and depacketizer in `rtc-rtp` (M).** RFC2198-3-2 to -8, 3-10, 3-11, 4-1: a `RedPacket`
   reader (block headers, bounds checks, primary/redundant split with timestamps and payload types) and a
   writer that takes a primary payload plus N earlier payloads. Needed for Opus RED interop with Chrome
   (`audio/red`) and as the carrier for ULPFEC (RFC 5109 section 14.2). Add a fuzz target for the reader.
2. **RED in negotiation (S).** RFC2198-5-2, 5-3: a `MIME_TYPE_RED` constant, an fmtp type that parses the
   slash list, checks every listed payload type is a format of the section, renumbers the list when the
   engine renumbers the codecs it refers to, and drops `red` when none of its block types was negotiated.
3. **Optional interceptor (M).** A send-side RED encoder that keeps the last N payloads per stream and a
   receive-side decoder that feeds recovered primaries back into the chain tagged like FEC recoveries, so
   NACK and the jitter buffer see one stream.
4. **Tests (S).** RFC2198-3-1, 5-1, 5-4, 6-1: an application-registered `red` negotiates, is sent with its
   payload type unmodified and is delivered.

## Bugs found

None in code that claims RED, because none does. One hazard for an application that registers `red`
itself: the RED fmtp names payload types, and nothing keeps them in step with the numbering the engine ends
up using. `MediaEngine::match_remote_codec` (`media_engine.rs:906-950`) translates `apt=` between remote and
local numbering for RTX only. Reproduction idea: register Opus at 111 and `audio/red` at 63 with fmtp
`111/111`; answer a remote offer that numbers Opus 96 and omits `red`; then create a new offer from this
side: Opus is offered under the negotiated number 96 while a re-offered `red` would still say `111/111`.
(Not run; whether `red` is re-offered at all after such an answer depends on the negotiated-codec list and
needs a test.)

## Status after the RTP wire work (`conf/rtp-wire`)

`rtc-rtp` now has the RED payload format, an encoder, a decoder and the fmtp list (`codec::red`). Open, outside `rtc-rtp`: `red` in negotiation (fmtp renumbering, the listed types on the `m=` line) and a RED interceptor.

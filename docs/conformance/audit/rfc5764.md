STANDING DEPARTURE from the SHOULD (listed in `docs/conformance.md`, "Standing departures from a SHOULD"), decided after two security reviews (`conf/dtls-resume-1`, `-2`; 2026-11-24), which found it safe and not cheap. Why the default is off: (1) it makes connections slower. The clause's strategy has the other associations wait for the first; on links with latency their handshakes then run after it instead of beside it. Measured by `tests/multi_transport_rtc2rtc.rs::the_session_costs_the_other_transports_the_first_handshake_on_links_with_latency` (three unbundled transports, time until every DTLS transport is connected): round trip 100 ms: off 453 ms, on against a peer that issues no ticket 753 ms (+300 ms, about 3 round trips, nothing resumed), on between two engines 703 ms (+250 ms, about 2.5 round trips); round trip 300 ms: 1.353 s, 2.253 s (+900 ms), 2.103 s (+750 ms). One datagram lost on the first handshake delays every transport instead of one (`a_datagram_lost_on_the_first_handshake_delays_every_transport_with_the_session_on`). What is saved is one signature and one verification per other transport (the clause is "as an optimization", written in 2010 against RSA and separate RTP and RTCP ports); (2) no browser can take part: libwebrtc sets `SSL_OP_NO_TICKET` with one `SSL_CTX` per adapter (rtc_base/openssl_stream_adapter.cc @ a222406d, lines 1223 and 1149), Firefox's `TransportLayerDtls::Setup()` (dom/media/webrtc/transport/transportlayerdtls.cpp) sets `SSL_ENABLE_SESSION_TICKETS` to `PR_FALSE` and `SSL_NO_CACHE` to `PR_TRUE`; against either the setting only adds the wait; (3) with BUNDLE there is one transport and the clause has nothing to act on. For default-on the others would have to start beside the first, which is no longer the clause's strategy. The reason is a repository measurement plus peers that cannot use it, but the setting is in no behaviour profile (`StrictRfc` does not turn it on), so the row stays `partial` (RULES.md), not `setting`; whether it becomes a `setting` row governed by `StrictRfc` is the coordinator's call. With it on: the first client transport of the negotiation that set up the transports runs a full handshake; the others wait for it, at most three of their initial flight intervals and never more than 3 s (then full handshakes), and resume with DTLS 1.3 tickets (`psk_dhe_ke` only; no DTLS 1.2 session id or ticket in any configuration); no wait for a ticket when none came before the server confirmed the handshake, when it is DTLS 1.2, or when the leader failed or could not start; only roles with more than one transport take part (a bundled connection exchanges no ticket); same remote fingerprints only, each section's fingerprint check run on the stored certificates, also for a final answer that names another certificate after a provisional one (both DTLS roles); never across connections; re-keying, later transports and a server's later handshake in place are full handshakes; client tickets kept at most 5 min and dropped once every member started; tickets and ticket keys wiped when the connection closes |

## Status of the gaps and bugs

The rows above carry the current verdicts; the lists below are the audit as it was made at 8916bc3.

- Fixed in `rtci-dtls`: gap 3 (MKI and profile count in the server's answer) and the last bug under "Bugs found" (a server without SRTP profiles ignores `use_srtp`). The other gaps and bugs are outside `rtci-dtls`.

## Gaps, in order of importance

1. **Associations without `use_srtp` cannot connect (S).** A peer that negotiates no SRTP profile (a
   data-channel-only DTLS stack) is refused as a server (`flight3.rs:224`, fatal alert) and, as a
   client, completes the DTLS handshake but `update_srtp_contexts` fails
   (`handler/dtls.rs:552`), so the transport never reports `Connected`. Make the SRTP contexts
   optional when no profile was negotiated and media sections are absent. Touches RFC5764-4.1-1,
   4.1.1-5.
2. **Key lifetime (S).** RFC5764-4.4-2: stop SRTCP at 2^31 instead of wrapping the index
   (`srtcp.rs:70`); decide whether SRTP for the AES-CM profiles stops at 2^31 (this RFC) or 2^48
   (RFC 3711) and document it; report the limit to the application so it can re-establish
   (RFC5764-4.4-1).
3. **MKI in the server's answer (S).** RFC5764-4.1.3-6/7: parse the MKI, abort with
   illegal_parameter when the server returns a non-empty one (the client always offers none).
   Add a test for a ClientHello carrying an MKI (RFC5764-4.1.3-5).
4. **Tests for implemented behaviour (S).** SRTP before handshake completion (5.1-1), a fixed
   exporter-to-key-layout vector (4.2-2), a ServerHello answering with an unoffered profile and with
   two profiles (4.1.1-3/4).
5. **Rekey support (L, probably never).** 4.3-1, 5.2-*: only reachable through a new DTLS
   association; RFC 8827 forbids renegotiation, so this is "new association keeps old keys for a
   grace period" at most.
6. **NULL profiles (not to be done).** 4.1.2-3/4 stay missing on purpose (RFC 8827 §6.5).

## Bugs found

- **SRTCP index wraps at 2^31 and reuses the keystream** (`rtci-srtp/src/context/srtcp.rs:70`).
  Reproduce: set an SSRC's `srtcp_index` to `MAX_SRTCP_INDEX` through a test hook, encrypt two
  RTCP packets; the second succeeds with index 0 instead of failing with
  `ErrExceededMaxPackets`.
- **A DTLS peer that does not negotiate `use_srtp` leaves the transport in `connecting`**
  (`src/peer_connection/handler/dtls.rs:543-552`, `:272-277`). Reproduce: drive a
  `DtlsHandler` as server against a `dtls::endpoint::Endpoint` client built with no SRTP
  profiles; `handle_read` returns `ErrNoSuchSrtpProfile` on the client's Finished, the queued
  server flight is not drained in that call, and `RTCDtlsTransportState` never becomes
  `Connected` (nor `Failed`).
- **Client accepts a ServerHello `use_srtp` with a non-empty MKI or several profiles**
  (`extension_use_srtp.rs:89-105`, `flight3.rs:186-203`). Reproduce: feed Flight3 a ServerHello
  whose `use_srtp` is `00 02 00 01 04 de ad be ef` (one profile, MKI of 4 bytes); the parse
  succeeds. Expected: illegal_parameter.
- **A generic `rtci-dtls` server with no SRTP profiles configured aborts on any client that offers
  `use_srtp`** (`flight0.rs:179-193`: an empty local list never matches). RFC 5764 §4.1.1 says to
  ignore the extension. Reproduce: `test_srtp_configuration` case "SRTP client only" documents it
  as expected behaviour; not reachable through `RTCPeerConnection`, which always configures
  profiles.

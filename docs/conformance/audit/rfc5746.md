## Gaps, in order of importance

1. **Validate renegotiation_info on both sides (S).** RFC5746-3.4-3, -3.4-4, -3.6-1, -3.6-2, -3.6-3.
   Parse the full `renegotiated_connection<0..255>`; in an initial handshake a non-empty value is a
   fatal handshake_failure; recognise the SCSV (0x00FF); answer with the extension only when the
   client signalled it (this also closes RFC5246-7.4.1.4-1 for this extension).
2. **no_renegotiation warning (S).** RFC5746-4.2-2. Answer a HelloRequest (client) or a ClientHello on
   a completed association (server) that arrives in the current epoch with a warning alert.
3. **Test that the ClientHello carries the extension (S).** RFC5746-3.4-1.
Renegotiation itself (3.5, 3.7) is not implemented and is not planned: DTLS 1.3 removed it, WebRTC
never uses it. It belongs in the "Not implemented, on purpose" table, which does not list it.

## Bugs found

A ServerHello or ClientHello whose renegotiation_info is not empty is accepted. Reproduction: feed a
client a ServerHello with extension `ff 01 00 0d 0c <12 bytes>`; expected fatal handshake_failure,
observed a warning log and a continuing handshake (`rtc-dtls/src/extension/renegotiation_info.rs:45`,
`handshake_message_server_hello.rs:141`). Not exploitable on its own, since nothing here ever
renegotiates.

# RFC 8837: Differentiated Services Code Point (DSCP) Packet Markings for WebRTC QoS

Spec: RFC 8837, January 2021 (Standards Track). Audited against fork master 8916bc3.
Sections covered: all (the normative text is in section 5).

The engine is sans-I/O and cannot set a DSCP itself. It could meet this RFC the way it handles ECN:
by returning, with every outgoing datagram, the codepoint the application's socket should use
(`TransportContext::ecn`, `rtci-shared/src/transport.rs:58`). There is no such field for DSCP, no
flow priority in the API (`RTCRtpEncodingParameters` has no `priority` / `networkPriority`;
`RTCPriorityType` does not exist) and no table. Every clause that asks for marking is therefore
`missing`, not `n/a`: the engine is the only place that knows which flow a datagram belongs to.

## Gaps, in order of importance

1. **DSCP guidance to the application (M).** One work package for the whole file: add
   `priority` and `network_priority` to `RTCRtpEncodingParameters` and data channel init
   (webrtc-priority), a `dscp: Option<u8>` in `TransportContext` filled on `poll_write` from RFC
   8837 Table 1 (audio/video flow type from the transceiver kind, LE for very-low), one value for
   all SCTP datagrams (highest data channel priority), one value for everything when the selected
   pair is TCP, STUN/DTLS handshake left at DF; call the SCTP association's congestion reset when
   the SCTP value changes. Tests: one per table cell at the `poll_write` boundary.

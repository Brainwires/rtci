# RFC 7742: WebRTC Video Processing and Codec Requirements

Spec: RFC 7742, March 2016 (Standards Track). Audited at fork master 8916bc3. Whole document covered
(sections 3 to 7).

The engine is a transport: it does not capture, encode, decode or render video. Those clauses are `n/a`.
What binds the engine is which video formats it offers with which SDP parameters, the RTP payload formats,
the CVO header extension, and the SDP attributes a sender must be able to see (`imageattr`, `max-fr`,
`max-fs`, the H.264 capability parameters).

One fact several rows depend on: the negotiated codec list holds the remote codec entries, remote fmtp
included (`src/peer_connection/configuration/media_engine.rs:1178-1218`). The peer's fmtp parameters are
therefore visible to the application through the sender's parameters, and an answer repeats the offer's
fmtp line.

## Gaps, in order of importance

1. **CVO negotiable out of the box (S).** RFC7742-4-1, 4-2, 4-4: register `urn:3gpp:video-orientation` in
   the default video header extensions (it costs nothing when the peer does not offer it), and add a test
   that a negotiated id is carried end to end on a written packet.
2. **Answer fmtp built locally (M, shared).** RFC7742-6.2-10 and RFC7587-7.1-8: never echo
   `sprop-parameter-sets` (or any offer-only parameter); keep the symmetric H.264 parameters, add the
   local ones.
3. **H.264 fmtp defaults and profiles (S).** RFC7742-6.2-7, 6.2-3: treat an absent `packetization-mode`
   as 0 and an absent `profile-level-id` as `42000A`; match Constrained High (`640c`) against a registered
   High entry the way libwebrtc's profile comparison does (constraint bits that do not change the decoder
   requirement), and consider a `640c1f` default entry.
4. **`imageattr`, `max-fr`, `max-fs` surfaced to the sender (M).** RFC7742-6-1, 6-2, 6.1-2, 6.2-9: parse
   `a=imageattr` and the codec limits into typed fields on the sender's parameters so the application's
   encoder can honour them, and let the application state its own.
5. **Pin the default video offer with a test (S).** RFC7742-5-2, 6.2-6: VP8 and an H.264 Constrained
   Baseline entry with `profile-level-id` and `packetization-mode=1` are present.

## Bugs found

1. **An answer can contain `sprop-parameter-sets`.** The negotiated codec is the remote entry with the
   remote fmtp (`media_engine.rs:1178-1218`), and the answer is written from it
   (`src/peer_connection/sdp/mod.rs:968`). Reproduction: apply an offer whose H.264 line is
   `a=fmtp:102 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42e01f;sprop-parameter-sets=Z0LAH9oBQBbsBEAAAAMAQAAADIPGDKg=,aM48gA==`
   and inspect `create_answer`: (expected) the same string, parameter sets included, appears in the answer,
   presenting the offerer's parameter sets as this endpoint's.
2. **Duplicate default registration (cosmetic).** `register_default_codecs` lists
   `packetization-mode=0;profile-level-id=42001f` at payload type 127 twice
   (`media_engine.rs:486-494` and `525-533`); the second is silently ignored by `add_codec`. No wire effect;
   one of them was probably meant to be another profile. Reproduction: read the list, or assert the number
   of H.264 entries registered against the number listed.

# RFC 10079 (Updates to the SFrame Cipher Suites Registry): clause-level audit

Spec: RFC 10079, "Updates to the SFrame Cipher Suites Registry", November 2026, Standards Track,
updates RFC 9605 (https://www.rfc-editor.org/rfc/rfc10079.txt). Engine: fork master ea78e88f
(v0.2.0), the `rtci-sframe` crate.

Finding (at ea78e88f): the crate already implemented everything RFC 10079 defines, from its
draft (draft-barnes-sframe-iana-256), before the RFC was published. The three suites of section
4.2 (0x0006 to 0x0008, AES-256-CTR with HMAC-SHA512 and 80-, 64- and 32-bit tags) are in
`CipherSuite` with the construction of RFC 9605 section 4.5.1 at the sizes section 2 gives (a
96-byte `sframe_key`: a 32-byte encryption subkey and a 64-byte authentication subkey; a 64-byte
tag before truncation), and the registry columns section 4.1 adds (`Nh`, `Nka`, `Nk`, `Nn`,
`Nt`) are `hash_len`, `aes_ctr_key_len`, `key_len`, `nonce_len` and `tag_len`. The stored
vectors (`rtci-sframe/src/test_vectors.rs`, `AES_256_CTR`) are byte for byte those of RFC 10079
Appendix A.2 (secret, key, salt and ciphertext of all three suites, compared by script on
2026-11-26). Appendix A.1 announces vectors of the AEAD on its own, but neither the RFC text nor
the JSON file it cites (bifurcation/sframe-iana-256, commit 78680b9) contains any: only the A.2
set. What this audit added: a test of the registry columns of Tables 1 and 2 for all eight
suites, and the RFC as the reference in place of the draft.

RFC 10079 has no RFC 2119 keyword. As in `rfc9605.md`, its algorithm definitions and registry
values are listed as MUST-level features: an implementation that does not follow them does not
interoperate. The registration procedure (section 4.1, last paragraph) is IANA's.

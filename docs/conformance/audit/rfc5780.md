# RFC 5780 conformance audit: NAT Behavior Discovery Using STUN

Spec: RFC 5780, May 2010 (Experimental). Audited at fork master `8916bc3`.

The engine does not use RFC 5780. What exists is attribute code points and two type aliases in
`rtc-stun`, with no behaviour behind them: nothing sends CHANGE-REQUEST, PADDING or
RESPONSE-PORT, nothing reads OTHER-ADDRESS or RESPONSE-ORIGIN from a response, and no NAT
mapping / filtering / lifetime / hairpin test exists (`grep` for the constants finds
`rtc-stun/src/attributes.rs:166-178`, `rtc-stun/src/addr.rs:117-125`, a codec test and a fuzz
target, nothing else). No README, `FORK.md` or `docs/conformance.md` row claims it. The clauses
of §3 and §4 (the discovery procedures) and §6 (server behaviour) are therefore not enumerated:
they bind a client or server that implements the usage, and this engine is neither. The rows
below are the parts a STUN agent meets without implementing the usage.

## Gaps, in order of importance

1. **Nothing to implement for WebRTC conformance.** RFC 5780 is experimental and outside the
   WebRTC specification set (RFC 8825 to 8835 do not reference it). The honest finite-list entry
   is one line in "Not implemented, on purpose": "STUN: NAT behaviour discovery (RFC 5780)". The
   constants can stay as code points (S, docs only).
2. **If it were wanted** (L): typed CHANGE-REQUEST / RESPONSE-PORT / PADDING attributes,
   RESPONSE-ORIGIN / OTHER-ADDRESS types bound to their own code points, and the §4 tests as a
   sans-I/O state machine over `rtc-stun::Client`. RFC5780-7.2-1, 7.3-1, 4-1, 3-1.
3. **RFC5780-6.1-1** is closed by the RFC 8489 work package on comprehension-required
   attributes (rfc8489.md, gap 2).

## Bugs found

1. **`ResponseOrigin` / `OtherAddress` encode as MAPPED-ADDRESS by default.**
   `rtc-stun/src/addr.rs:117-125`: both are plain aliases of `MappedAddress`, whose
   `Setter::add_to` writes attribute type 0x0001 and whose `Getter::get_from` reads 0x0001.
   Reproduction: `OtherAddress { ip, port }.add_to(&mut m)` then `m.contains(ATTR_OTHER_ADDRESS)`
   is false and `m.contains(ATTR_MAPPED_ADDRESS)` is true. (`AlternateServer` has the same
   shape.) Harmless today because nothing uses them; a caller has to know to use `add_to_as`.

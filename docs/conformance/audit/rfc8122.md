# RFC 8122 conformance audit: the SDP fingerprint attribute (connection-oriented media over TLS)

Spec: RFC 8122, March 2017 (obsoletes RFC 4572). Audited at fork master 8916bc3. Only the parts
DTLS-SRTP inherits bind this engine: the `a=fingerprint` attribute (§5) and certificate
presentation (§6.2); the `TCP/TLS` protocol identifier (§4) and the identity rules for SDP
without integrity protection (§6.1, §7) are marked n/a. Code read:
`src/peer_connection/certificate/mod.rs`, `src/peer_connection/transport/dtls/{mod,fingerprint}.rs`,
`src/peer_connection/sdp/mod.rs` (`extract_fingerprints`, fingerprint writers),
`rtc-dtls/src/flight/flight{4,5}.rs`. All sections done.

## Gaps, in order of importance

1. **More hash functions for verification (S).** RFC8122-5-11 (and RFC8842-5.1-6): verify against
   sha-384 and sha-512 (and sha-1 / sha-224 if the provider has them) when the peer offers no
   sha-256, choosing the strongest one offered; test "sha-512 only" and "md5 only is refused"
   (RFC8122-5-5).
2. **Fingerprint for the signature hash (S).** RFC8122-5-8: when a certificate is signed with
   SHA-384 / SHA-512, also publish a fingerprint with that hash (`get_fingerprints` needs the
   signature algorithm, which `x509-parser` already gives).
3. **Syntax validation (S).** RFC8122-5-4: refuse a fingerprint whose value is not colon-separated
   hex of the hash's length, at `set_remote_description` rather than at the handshake.
4. **Alert when the client sends no certificate (S).** RFC8122-6.2-5: bad_certificate instead of
   no_certificate, or record the deviation (TLS 1.2 itself would use handshake_failure).
5. **Listening before the answer (M).** RFC8122-6.2-6: shared with RFC8842-5.2-4.
6. **Tests (S).** Uppercase output (5-3); NULL-suite ClientHello refused (7-1).

## Bugs found

- **A peer whose only fingerprint is not sha-256 can never connect**
  (`src/peer_connection/transport/dtls/mod.rs:242-247`). Reproduce: rewrite the offer's
  `a=fingerprint:sha-256 ...` to the certificate's real `sha-512` hash; the answerer fails the
  handshake with `ErrUnsupportedFingerprintAlgorithm` although the certificate is the right one.
- **`RTCCertificate::get_fingerprints` returns a fingerprint for every certificate of a chain**
  (`src/peer_connection/certificate/mod.rs:727`), so a certificate built with
  `from_pkcs8(chain of 2)` advertises its issuer's fingerprint as if it were an end-entity
  certificate; the verifier only ever hashes the leaf (`transport/dtls/mod.rs:255`). Reproduce:
  build an `RTCCertificate` from a two-certificate chain and count `a=fingerprint` lines in the
  offer (2, expected 1).
- **Malformed fingerprint values are accepted until the handshake**
  (`src/peer_connection/sdp/mod.rs:1655-1662`). Reproduce: `set_remote_description` with
  `a=fingerprint:sha-256 zz` succeeds; the failure only shows as a DTLS `failed` state later.

## Gaps, in order of importance

1. **Drop unknown ranges in the demultiplexer (S).** RFC7983-7-6: replace the catch-all with an
   explicit `[0..3]` match for STUN and a counted drop for everything else; add a table-driven
   test over all 256 first bytes (bounds 3/4, 19/20, 63/64, 127/128, 191/192 included).
2. **STUN classification by first byte (S).** RFC7983-7-1: `is_stun_message` should also require
   the two top bits of the first byte to be zero, as RFC 8489 §6 does.

## Bugs found

- **Out-of-range datagrams mark a remote candidate as seen**
  (`rtc-ice/src/agent/mod.rs:1848-1857`, reached from `demuxer.rs:113`). A datagram with first
  byte 4..19, 64..127 or 192..255 from a remote candidate's address calls
  `remote_candidates[i].seen(now, false)` before it is discarded. Reproduce: connect two peers,
  inject `[0x50; 16]` from the remote candidate's address, and compare the candidate's
  last-received time before and after.
- **One `warn!` and one returned error per junk datagram** (`rtc-ice/src/agent/mod.rs:1917-1929`):
  anyone who can reach the socket can fill the log. Reproduce: feed 10 000 datagrams with first
  byte 0x90..0xBF excluded (say 0x05) and count log records.
- **A datagram with first byte 192..255 and the STUN magic cookie at offset 4 is decoded as STUN**
  (`rtc-stun/src/message.rs:105`). Reproduce: take a valid Binding request, set bit 7 of byte 0,
  feed it; `handle_inbound_candidate_msg` enters `Message::decode` instead of discarding.
  Authentication still protects the agent; this is a classification error only.

## Status after `conf/dtls-sdp-1`

Gap 1 is closed: the demultiplexer matches the ranges explicitly and drops the rest
(`demuxer.rs::every_first_byte_goes_to_its_protocol_or_is_dropped`). Of the three bugs, the
first two are fixed for every first byte outside 0 to 3
(`demuxer.rs::out_of_range_datagrams_do_not_reach_the_ice_agent`), and the third no longer
reaches the agent through a peer connection. Left in `rtc-ice` / `rtc-stun`: a datagram whose
first byte is 0 to 3 and that is not STUN still marks the candidate as heard from and logs a
warning, and `is_stun_message` does not look at the two top bits (gap 2).

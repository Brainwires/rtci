# RFC 7022: Guidelines for Choosing RTP Control Protocol (RTCP) Canonical Names (CNAMEs): clause audit

Spec: RFC 7022, September 2013 (obsoletes RFC 6222, updates RFC 3550). Audited at fork master 8916bc3.

What the engine does: a sending SSRC's CNAME, in SDP (`a=ssrc:<ssrc> cname:`,
`src/peer_connection/sdp/mod.rs:1242-1259`) and in RTCP SDES
(`src/peer_connection/handler/interceptor.rs:260-266`), is the `stream_id` of its track: the
MediaStream id string the application passed to `MediaStreamTrack::new`. Receiver reports, which
are sent from random SSRCs that belong to no sender, use a per-connection CNAME made of 16 hex
digits of one random `u64` (`handler/interceptor.rs:267-272`). RTX and FlexFEC SSRCs get the
track's `stream_id` in SDP and no SDES at all. `RTCRtcpParameters::cname` is never filled.

Totals (MUST includes MUST NOT, SHALL, REQUIRED; SHOULD includes SHOULD NOT, RECOMMENDED):

- MUST: tested 1 / untested 0 / partial 2 / missing 0 / violated 3 / n-a 1
- SHOULD: tested 1 / untested 0 / partial 0 / missing 0 / violated 1 / n-a 0

## Gaps, in order of importance

1. **One RFC 7022 CNAME per peer connection** (RFC7022-4.1-1, 4.2-1, 4.2-3, 4.2-5, 4.2-6, 5-1). Size S to M. Generate
   12 random octets (CSPRNG) when the peer connection is created, Base64 encode them to a 16-character
   string, and use that one string as the CNAME of every local SSRC: senders, RTX, FlexFEC and the
   receiver-report SSRCs, in `a=ssrc ... cname:` and in every SDES. Stop deriving it from the MediaStream
   id (the msid already carries that). Fill `RTCRtcpParameters::cname` with it. Tests: two tracks in
   different streams advertise and send the same CNAME; the CNAME is 16 Base64 characters; two peer
   connections get different CNAMEs; `replace_track` does not change it.

## Bugs found

- **B1. Audio and video in different MediaStreams cannot be synchronised.** `src/peer_connection/sdp/mod.rs:1242`
  and `handler/interceptor.rs:260-266` use the stream id as CNAME. Reproduction: add an audio track with
  stream id `a` and a video track with stream id `v`, negotiate, read the offer: `a=ssrc:X cname:a` and
  `a=ssrc:Y cname:v`; the SDES of the two sender reports differ the same way. A browser receiving this
  treats the two as different synchronisation sources and plays them unsynchronised.
- **B2. The receiver-report CNAME has 64 bits of entropy and differs from the senders' CNAME.**
  `handler/interceptor.rs:271`. Reproduction: in a sendrecv call, capture one SR compound and one RR
  compound from the same endpoint: two different CNAMEs, the RR one being 16 hex digits.

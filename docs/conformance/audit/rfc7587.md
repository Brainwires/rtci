# RFC 7587: RTP Payload Format for the Opus Speech and Audio Codec

Spec: RFC 7587, June 2015 (Standards Track). Audited at fork master 8916bc3. Whole document covered
(sections 3 to 8).

The engine is a transport: it neither encodes nor decodes Opus. Clauses about the encoder, the decoder or
capture are `n/a`. What binds the engine is the RTP usage (section 4), the packetizer / depacketizer in
`rtc-rtp/src/codec/opus/`, and the SDP mapping and offer/answer rules (section 7).

Two facts about the code that several rows depend on:

- The engine's send path (`RTCRtpSender::write_rtp`) forwards the application's RTP packets; it does not
  packetize. `rtc_rtp::packetizer::new_packetizer` is public API used by the examples and by tests, and is
  audited here as the crate's packetizer.
- After a remote description is applied, the negotiated codec list holds the **remote** codec entries
  (remote payload type and remote fmtp line): `MediaEngine::update_from_remote_description`
  (`src/peer_connection/configuration/media_engine.rs:1178-1218`) pushes `remote_codec`, and the SDP writer
  emits `codec.rtp_codec.sdp_fmtp_line` (`src/peer_connection/sdp/mod.rs:968`). An answer therefore repeats
  the offer's fmtp line.

## Gaps, in order of importance

1. **Answer fmtp is the offerer's, not ours (M).** RFC7587-7.1-8, RFC7587-3.3-2. Generate the answer's
   fmtp from the locally registered codec (keeping only what the format requires to be symmetric, such as
   H.264 `profile-level-id` / `packetization-mode`), and keep the remote's line separately as "what the
   peer can receive" for the sender's parameters. Affects every codec, not only Opus.
2. **Audio marker bit in the packetizer (S).** RFC7587-4.1-2: a per-payloader rule (video: last packet of
   the frame; audio: first packet after a gap signalled through `skip_samples`, otherwise 0).
3. **Duplicate suppression without the jitter buffer (S).** RFC7587-4.1-4: drop a de-encapsulated RTX
   packet whose original sequence number was already delivered on the primary SSRC (a small per-SSRC
   replay window after RTX de-encapsulation).
4. **`ptime` / `maxptime` (S).** RFC7587-7-2, 7.1-2: parse both attributes, expose them, write them when
   the application sets them.
5. **rtpmap validation (S).** RFC7587-7-1: reject or ignore a remote `opus` whose rtpmap is not
   `48000/2`, and make codec matching compare clock rate and channels.
6. **Tests (S).** RFC7587-3.3-2, 4.1-3, 4.1-5, 7-3, 7-4: the default offer's Opus lines.

## Bugs found

1. **Every Opus packet from `new_packetizer` has the marker bit set.**
   `rtc-rtp/src/packetizer/mod.rs:144` sets `marker` on the last payload of each `packetize` call, the video
   rule. With `OpusPayloader` (one payload per call) and `G7xxPayloader` (last fragment per call) that marks
   every audio packet as the start of a talkspurt (RFC 3551 4.1). Receivers that reset their jitter buffer
   or playout on the marker are disturbed. Reproduction: `new_packetizer(.., Box::new(OpusPayloader), ..)`,
   call `packetize` three times, assert `header.marker` is false on the second and third packet (fails
   today).
2. **The answer echoes the offer's fmtp.** `update_from_remote_description`
   (`media_engine.rs:1178-1218`) stores the remote codec entries as the negotiated codecs and the answer is
   written from them. Reproduction: register Opus locally with `minptime=10;useinbandfec=1;stereo=1`; apply
   an offer with `a=fmtp:111 minptime=10;useinbandfec=0;x-unknown=7`; `create_answer` (expected) contains
   `useinbandfec=0;x-unknown=7` and no `stereo=1`. RFC 7587 7.1 requires the unknown parameter to be removed
   and treats each side's parameters as its own.

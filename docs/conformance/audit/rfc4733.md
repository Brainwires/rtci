# RFC 4733: RTP Payload for DTMF Digits, Telephony Tones, and Telephony Signals

Spec: RFC 4733, December 2006 (Standards Track; obsoletes RFC 2833; updated by RFC 4734 and RFC 5244).
Audited at fork master 8916bc3. Sections covered: 2 (named events), 3 (DTMF), 4 (tones), 6 (security),
7 (IANA and media types). Sections 1 and 5 are descriptive or examples.

**Status of the implementation.** The engine has the MIME constant
(`MIME_TYPE_TELEPHONE_EVENT`, `media_engine.rs:191`) and maps it to the pass-through `G7xxPayloader`
(`rtp_codec.rs:114-120`). That is all:

- no telephone-event payload type in `rtc-rtp` (no builder, no parser);
- not in `register_default_codecs`, so the default SDP does not offer it;
- no DTMF sender (`RTCDTMFSender` is in the "Not implemented, on purpose" table of `docs/conformance.md`:
  "the engine sends the telephone-event packets it is given").

So every sending-procedure clause is `missing` and counted, as the audit rules require for "on purpose"
items. Receiving procedures that are about playing tones out are `n/a` (the engine renders nothing; RFC 7874
section 3 lets a WebRTC endpoint drop received events). What the engine does provide, read from the code:
a packet whose payload type is any negotiated codec of the sender is sent on the audio SSRC unchanged
(`rtp_sender/mod.rs:449-451`), and any payload type arriving on a known SSRC is delivered to the application
(`handler/endpoint.rs:262-280`).

## Gaps, in order of importance

1. **telephone-event payload type in `rtc-rtp` (S).** RFC4733-2.3-1, 2.3.3-1, 2.3.4-1, 2.3.5-1, 3.2-1, 7-1:
   a `TelephoneEvent { event, end, volume, duration }` with marshal / unmarshal, the DTMF code table
   (0-9, *, #, A-D), bounds checks and a fuzz target.
2. **DTMF sender (M).** RFC4733-2.1-1, 2.2.2-1, 2.5.1.2-1 to -5, 2.5.1.3-1, 2.5.1.4-1, 2.5.1.4-4, 2.5.1.6-1,
   plus the RFC 7874 duration and gap limits: a sans-I/O tone queue on the sender (`insert_dtmf(tones,
   duration, gap)`, driven from `handle_timeout`) that emits event packets in the audio stream's sequence
   and timestamp space: M on the first, updates every 50 ms with the same timestamp and growing duration,
   segmentation at 0xFFFF units, three end packets with E. This is what W3C `RTCDTMFSender` needs
   underneath and removes the row from "Not implemented, on purpose".
3. **Offer it and keep it offered (S).** RFC4733-2.5.2.1-1, 2.5.1.1-1 to -3, Bug 1: register
   `telephone-event/8000` and `/48000` with fmtp `0-15` in the default codecs (RFC 7874 requires the
   format), parse the peer's event list, restrict sending to it, and stop
   `codec_preferences_from_encodings` from dropping the format.
4. **Per-payload-type clock rate in receive statistics (S).** RFC4733-2.5.2.2-4: jitter for packets whose
   payload type has another clock rate than the stream's primary codec.
5. **RFC 2198 combinations and the tone payload (M, low value).** RFC4733-2.5.1.1-4, 2.5.1.3.1-1,
   2.5.1.4-2, 2.5.1.4-3, 2.6.2-1, 4.x: depend on RED; `audio/tone` is not used by WebRTC.

## Bugs found

1. **A sender whose track names its codec loses telephone-event from the offer.**
   `codec_preferences_from_encodings` (`src/peer_connection/internal.rs:2108-2161`) builds the transceiver's
   codec preferences from the encodings' codecs plus "the repair formats that accompany them", using
   `is_repair_codec` (`rtp_codec.rs:312-319`: `rtx`, `ulpfec`, `red`, `flexfec*`). `audio/telephone-event`
   (and `audio/CN`) accompany the media codec in exactly the same way but are not in that set, so they are
   filtered out. Reproduction: register Opus and `audio/telephone-event` (PT 126, clock 8000, fmtp `0-15`)
   in the media engine, `add_track` an audio track whose coding names Opus, `create_offer`: (expected)
   the audio section has no `telephone-event` rtpmap, and a later `write_rtp` with PT 126 is rewritten to
   the Opus payload type by the fallback at `rtp_sender/mod.rs:449-480`, turning the event into a corrupt
   Opus packet. With a track that names no codec the format is offered.

## Status after the RTP wire work (`conf/rtp-wire`)

`rtc-rtp` now has the payload type, the DTMF table, the `events` list, and sender and receiver state machines (`codec::telephone_event`). Open, outside `rtc-rtp`: a DTMF sender in the engine that paces the packets in the audio stream's sequence and timestamp space, offering the format by default, bug 1 (`codec_preferences_from_encodings`), the per-payload-type clock in receive statistics, RFC 2198 combinations and the tone payload.

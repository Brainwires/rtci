# RFC 9146 conformance audit: Connection Identifier for DTLS 1.2

Spec: RFC 9146, March 2022. One row per normative sentence (the text of the clause, cut to 25 words), plus rows marked "Implicit".

Connection ids are implemented for both versions: DTLS 1.2 by this RFC (the `connection_id` extension in the DTLS 1.2 hellos, the `tls12_cid` record with its changed MAC and AEAD input, the address rule of section 6), DTLS 1.3 by RFC 9147 section 9 (`rfc9147.md`). A ClientHello carries one `connection_id` extension for whichever version is negotiated; by default it asks for no id (`Some(0)`). RFC 9146 has no test vectors, and OpenSSL 4.1 has no DTLS connection ids, so the record format is checked against the RFC's text built byte by byte and by two engine endpoints; OpenSSL and webrtc 0.17 were checked to ignore the extension (container, both roles).

## Gaps, in order of importance

1. **Interop of the tls12_cid record (S, outside the container).** Mbed TLS and wolfSSL implement RFC 9146; neither is in the test image. A recording from either would add known answers for the record format.
2. **Renegotiation with connection ids (n/a here).** RFC 9146 says the ids of the current epoch stay until the new epoch; this stack refuses renegotiation (no_renegotiation, RFC 8827 section 6.5), so the case does not arise.

# RFC 6904 — Encryption of Header Extensions in SRTP: clause audit

Spec: RFC 6904, April 2013 (current). Audited against fork master 8916bc3. Read-only audit; no test
was run. SHALL / REQUIRED count as MUST; RECOMMENDED as SHOULD.

**The RFC is not implemented.** There is no `urn:ietf:params:rtp-hdrext:encrypt` handling anywhere in
the tree (searched `src/`, `rtc-srtp/`, `rtc-sdp/`, `rtc-rtp/`), no header-extension key derivation
(labels 0x06 / 0x07; `rtc-srtp/src/key_derivation.rs:6-11` stops at 0x05) and no encryption mask.
Header-extension confidentiality is offered through Cryptex (RFC 9335) instead, which RFC 9335 §5
recommends over this mechanism. RFC 6904 is not in the "Not implemented, on purpose" table of
`docs/conformance.md`; it should be added there if that is the decision.

## Gaps, in order of importance

1. **Decide and record (S)** — add RFC 6904 to "Not implemented, on purpose" in `docs/conformance.md`,
   or implement it. Browsers (libwebrtc) do not negotiate RFC 6904 by default and offer Cryptex, so
   leaving it out costs no browser interop.
2. **Test the refusal path (S)** — 4.1-1: an offer carrying
   `a=extmap:3 urn:ietf:params:rtp-hdrext:encrypt urn:ietf:params:rtp-hdrext:ssrc-audio-level` must be
   answered without that extmap and with the clear form negotiated if it was offered as well.
3. **Full implementation (L)** — 3-1 to 3-6, 3.2-1, 3.2-2, 4-1 to 4-5, 4.1-2, 4.1-4, plus RFC 7714 §8.3:
   KDF labels 0x06 / 0x07 (128 and 256), header keystream with the payload IV, mask construction for
   one- and two-byte extensions, extmap parsing / generation with the `encrypt` URI, per-id negotiation
   state handed to the SRTP contexts, mutual exclusion with Cryptex per packet (RFC 9335 §5), and the
   RFC 6904 Appendix A test vectors.

## Bugs found

None (nothing implemented). Not verified by a test: behaviour when a peer offers an `encrypt` extmap
(see gap 2); reproduction idea is the offer in gap 2 fed to `set_remote_description` + `create_answer`.

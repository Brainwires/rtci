# RFC 6904 — Encryption of Header Extensions in SRTP: clause audit

Spec: RFC 6904, April 2013 (current). Audited against fork master 8916bc3; verdicts updated for branch `conf/srtp-conformance`. Read-only audit; no test
was run. SHALL / REQUIRED count as MUST; RECOMMENDED as SHOULD.

**On fork master the RFC was not implemented; the branch implements the transform (section 3) in
`rtc-srtp` and leaves the signalling (section 4) open.** On master there is no `urn:ietf:params:rtp-hdrext:encrypt` handling anywhere in
the tree (searched `src/`, `rtc-srtp/`, `rtc-sdp/`, `rtc-rtp/`), no header-extension key derivation
(labels 0x06 / 0x07; `rtc-srtp/src/key_derivation.rs:6-11` stops at 0x05) and no encryption mask.
Header-extension confidentiality is offered through Cryptex (RFC 9335) instead, which RFC 9335 §5
recommends over this mechanism. RFC 6904 is not in the "Not implemented, on purpose" table of
`docs/conformance.md`; it should be added there if that is the decision.

## Open after `conf/srtp-conformance`

The transform (section 3) is implemented and tested in `rtc-srtp`:
`Context::set_encrypted_header_extensions` takes the ids, for every profile (AES-CM 128 / 192 / 256,
NULL, and the AEAD profiles as RFC 7714 section 8.3 has it), with the RFC's Appendix A vectors and
libsrtp's known answers for AES-CM and AEAD_AES_128_GCM.

1. **Signalling (L, SDP / peer connection)**: 4-1 to 4-5, 4.1-2, 4.1-4. `a=extmap:<id>
   urn:ietf:params:rtp-hdrext:encrypt <uri>` is neither parsed nor generated, so no peer connection
   uses the transform. The negotiated ids go to both SRTP contexts with
   `set_encrypted_header_extensions`; a header parsed before `decrypt_rtp_with_header` holds
   ciphertext in those elements and must be parsed again from the returned packet.
2. **Refusal path (S, peer connection)**: 4.1-1, still untested.

## Status after the header extension work (`conf/jsep-18-header-extensions`)

Section 4 is implemented: the encrypted form is written and read, offered best effort for the
audio level extensions by default (`RTCRtpHeaderExtensionEncryption`), preferred when answering
(the clear form answered `inactive`), and the negotiated ids reach both SRTP contexts
(`update_encrypted_header_extensions`), also after a later DTLS handshake. A header parsed by the
engine is always parsed from the packet `decrypt_rtp` returned, so it holds plaintext.

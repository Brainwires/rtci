# RFC 3611: RTP Control Protocol Extended Reports (RTCP XR)

Spec: RFC 3611, November 2003. Audited against fork master 8916bc3. Scope: 2 (XR packet), 3 (block
framework), 4.1-4.7 (the seven block types), 5 (SDP signalling), 7 (security). Section 6 (IANA) binds
nobody. Later XR block types (RFC 5725, 6776, 6798, 6843, 6958, 7002-7005, 7097, 7243, 7244, 7294 ...)
are outside this audit; they parse as `UnknownReportBlock`.

What exists:

- **Wire codec for the XR packet and all seven RFC 3611 block types**:
  `rtci-rtcp/src/extended_report/{mod,rle,prt,rrt,dlrr,ssr,vm,unknown}.rs`. One round-trip test
  (`extended_report_test.rs::test_encode`, `::test_decode`, one fixture with all seven blocks) and nine
  fuzz targets (`rtci-rtcp/fuzz/fuzz_targets/extended_report_*`).
- **Behaviour for the RTT pair only**: `ReceiverReportInterceptor` adds a Receiver Reference Time block
  to each RR of a stream that negotiated the non-standard `a=rtcp-fb:<pt> rrtr`
  (`rtci-interceptor/src/report/receiver.rs:252-263`); `SenderReportInterceptor` records every reference
  time it receives and answers once with a DLRR block in the next SR
  (`report/sender.rs:231-252`, `:303-326`); the statistics accumulator turns an inbound DLRR into
  `roundTripTime` on `remote-outbound-rtp` (`src/statistics/accumulator/rtcp_reports.rs:81-94`,
  `rtp_stream/inbound.rs:194-225`).
- **Nothing generates** Loss RLE, Duplicate RLE, Packet Receipt Times, Statistics Summary or VoIP
  Metrics blocks, and nothing consumes them when received (they stop at the chain's terminus).
- **No `a=rtcp-xr` SDP attribute**: not written, not parsed (`grep rtcp-xr` finds nothing in `src/` or
  `rtci-sdp/`).

## Gaps, in order of importance

1. **Robust XR parsing (S).** IDs 2-4, 4-2, 2-5, 4.1-10. Honour the RTCP padding bit in
   `ExtendedReport::unmarshal`; on a block that fails its own parse, skip it by its declared length (keep
   it as `UnknownReportBlock`) instead of failing the packet; round RLE blocks up with a terminating
   null chunk when marshalling; refuse or pad an `UnknownReportBlock` body that is not a multiple of 4,
   and keep its block type and type-specific octet so it re-marshals as what it was.
2. **`a=rtcp-xr` signalling (M).** IDs 5-2, 5.1-1, 5.1-2, 5.1-3, 5.1-5, 5.1-6, 5.2-1..5.2-4. Parse and
   write the attribute at session and media level (`rcvr-rtt=all|sender[:max]` first), gate RRTR and
   DLRR on it, keep `rrtr` as the libwebrtc alias. Without this, the claim "RTCP XR (RFC 3611)" is the
   RTT pair as Chrome signals it, nothing more.
3. **DLRR from a receive-only endpoint (S).** ID 4.5-3. Attach the DLRR to an RR when there is no SR to
   carry it (allowed under `rcvr-rtt=all`), so a peer measuring RTT against a pure receiver gets an
   answer.
4. **Statistics Summary and VoIP Metrics generation (M each).** IDs 4.6-2, 4.6-3, 4.6-6, 4.7-2,
   4.7.1-1 .. 4.7.7-1. The receiver-report stream already has loss, duplicate and jitter counters and
   the engine has jitter buffers; a generator interceptor could fill both blocks. VoIP Metrics needs
   the Appendix A.2 burst/gap model.
5. **Loss RLE / Duplicate RLE / Packet Receipt Times generation and consumption (M).** IDs 4.1-2 ..
   4.1-11, 4.1.1-1, 4.2-2, 4.3-2 .. 4.3-4. Trace builder with thinning and the Appendix A.1 sequence
   accounting; a reader that expands chunks into per-packet flags. RFC 8834 does not require any of
   them; if they are not going to be built, say so in "Not implemented, on purpose" (today the codec's
   presence implies more than exists).
6. **Tests (S).** IDs 2-3, 4.4-2, 4.5-2, 4.1-5, 5.1-4; a unit test in `rtci-interceptor` for
   RRTR-in / DLRR-out with a known delay (4.5-5 is only covered end to end, by "an RTT exists").

## Bugs found

1. **A padded XR packet fails to parse and takes the compound datagram with it.**
   `rtci-rtcp/src/extended_report/mod.rs:285`: the block loop runs until the buffer is empty and never
   looks at `header.padding`. Reproduce: marshal an XR with one RRTR block, append four padding octets
   `00 00 00 04`, set the P bit and add 1 to the length; `ExtendedReport::unmarshal` returns
   `PacketTooShort` (the padding is read as BT=0, length 4 words). Put an RR in front and
   `rtcp::packet::unmarshal` loses the RR too.
2. **An RLE block with an odd number of chunks is marshalled misaligned.** `rle.rs:154`:
   `block_length = raw_size()/4 - 1` truncates when `chunks.len()` is odd, and `marshal_to` writes the
   2 extra octets anyway; `ExtendedReport::header` then sets the RTCP P bit and appends RTCP padding
   (`mod.rs:193`, `:256`), so the receiver sees a block whose length excludes its last chunk, followed
   by a stray chunk and padding parsed as further blocks. RFC 3611 4.1 requires a terminating null
   chunk instead. Reproduce: marshal `ExtendedReport { reports: [LossRLEReportBlock { chunks:
   [Chunk(0x4006)], .. }] }` and unmarshal the bytes: the result is not equal to the input (or is an
   error).
3. **An unknown block does not survive a round trip.** `unknown.rs:21-23`: `xr_header()` always writes
   BT=0 and type-specific 0, so a block of type 8 (or any later-RFC type) that was parsed and is
   marshalled again changes type. Only matters to an application that forwards XR; reproduce by
   unmarshalling an XR with a BT=14 block and marshalling it back.
4. **One malformed block fails every RTCP packet in the datagram.** `rrt.rs:107`, `dlrr.rs:135`,
   `ssr.rs`, `vm.rs`, `prt.rs`, `rle.rs`: a known block type with an unexpected length returns
   `PacketTooShort`. Reproduce: `SR + XR(RRTR with block length 3 and 12 octets of body)` through
   `rtcp::packet::unmarshal`; the SR is lost, so the receiver's LSR/DLSR and the stats miss a report
   because of an extension block they do not need.
5. **`VoIPMetricsReportBlock::default()` is not "everything unavailable".** `vm.rs`: the derived
   default is all zeros, which for signal level, noise level, RERL, R factor, ext. R factor, MOS-LQ and
   MOS-CQ are real values (0 dBm0, R = 0 ...); RFC 3611 4.7.4/4.7.5 use 127 for "unavailable", and
   Gmin must not be 0 (4.7.6). An application filling a few fields over `..Default::default()` sends
   false metrics. Reproduce: marshal the default and read octets 20-27 and 23 (Gmin).

## Status after `conf/rtcp-codec` (rtci-rtcp)

- Bugs 1 to 5 fixed. Gap 1 (robust XR parsing) closed.

- Still open, all outside the codec: `a=rtcp-xr` signalling, DLRR from a receive-only endpoint, and

# RFC 3389: RTP Payload for Comfort Noise (CN)

Spec: RFC 3389, September 2002 (Standards Track). Audited at fork master 8916bc3. Whole document covered
(sections 3 to 7).

**Status of the implementation.** There is no comfort-noise support in the engine beyond one table entry:
`static_audio_payload_type` (`src/peer_connection/sdp/mod.rs:2106-2119`) knows that payload type 13
without an rtpmap is `CN/8000`. There is no `MIME_TYPE_CN` constant, `audio/CN` is not in
`register_default_codecs`, `RTCRtpCodec::payloader` has no entry for it (`rtp_codec.rs:94-127` returns
`ErrNoPayloaderForCodec`), and `rtc-rtp` has no CN payload type. Noise analysis and synthesis (VAD, DTX,
CNG) are codec work and `n/a`; the payload format, its RTP usage and its SDP are transport work and are
listed as `missing`. An application can register `audio/CN` itself, write CN packets it built through
`write_rtp` (any negotiated payload type is forwarded on the audio SSRC, `rtp_sender/mod.rs:449-451`) and
receives CN packets on the track (`handler/endpoint.rs:262-280`).

RFC 7874 section 3 makes RFC 3389 CN a MUST for WebRTC endpoints with G.711 (which the engine offers by
default) and any other codec without its own CN; see `rfc7874.md`.

## Gaps, in order of importance

1. **Offer CN for the codecs that need it (S).** RFC3389-4-2, 5.1-1, and RFC 7874's MUST: a
   `MIME_TYPE_CN` constant, `CN/8000` at static payload type 13 next to PCMU/PCMA/G722 in the default
   codecs (and decide whether to offer dynamic `CN/16000`, `CN/32000` as browsers do; not `CN/48000` with
   Opus, which RFC 7874 discourages), a pass-through payloader entry so `payloader()` does not fail, and
   the codec-preference fix of Bug 2.
2. **CN payload type in `rtc-rtp` (S).** RFC3389-3-1, 3-2, 3.3-1, 4-4: a small
   `ComfortNoise { level, coefficients }` with marshal / unmarshal and a level bound check, so an
   application or a future DTX helper does not hand-roll bytes.
3. **Do not rewrite an unnegotiated payload type into the media codec's (S).** Bug 1.
4. **Tests (S).** RFC3389-5-1, 5.1-2: CN negotiated and sent on the audio SSRC arrives with its payload
   type; a remote offer with a bare `13` is answered with 13 when CN is registered.

## Bugs found

1. **A CN (or DTMF) packet sent when its format was not negotiated becomes a media packet.**
   `RTCRtpSender::write_rtp` (`src/rtp_transceiver/rtp_sender/mod.rs:449-476`) rewrites any payload type
   that is not in the sender's negotiated codecs to the payload type of the encoding's codec. For a CN
   packet (1 to 13 bytes of noise parameters) the peer then decodes those bytes as PCMU/Opus audio.
   Reproduction: negotiate PCMU only, call `write_rtp` with a packet whose payload type is 13 and a one-byte
   payload; the packet leaves with payload type 0. Dropping (or returning an error) is the safe behaviour
   for a payload type that names a different, known format.
2. **`audio/CN` is filtered out of the offer for a track that names its codec**, for the same reason as
   telephone-event (`codec_preferences_from_encodings`, `src/peer_connection/internal.rs:2108-2161`, keeps
   only `is_repair_codec` formats besides the named codec). Reproduction: register PCMU and `audio/CN`
   (PT 13, clock 8000), `add_track` a PCMU track, `create_offer`: (expected) the `m=audio` line lists 0 and
   not 13.

## Status after the RTP wire work (`conf/rtp-wire`)

`rtc-rtp` now has the CN payload (`codec::comfort_noise`) and a payloader that never sets the marker. Open, outside `rtc-rtp`: offering CN (payload type 13 and dynamic types), `MIME_TYPE_CN` and its `payloader()` entry, and bugs 1 and 2.

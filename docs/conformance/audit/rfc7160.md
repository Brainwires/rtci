# RFC 7160: Support for Multiple Clock Rates in an RTP Session

Spec: RFC 7160, April 2014 (Standards Track, updates RFC 3550). Audited against fork master
8916bc3. Sections covered: 3 and 4 (all normative text). Referenced by RFC 8834 4.3.

How the engine stands: a stream (local or remote) is bound to the interceptor chain once, with one
`StreamInfo` carrying one clock rate. For a remote stream that is the codec of the first payload
type seen (`handler/interceptor.rs:336`); the binding is not redone when the payload type changes.
For a local stream a re-binding happens only on renegotiation (`rebind_local_streams`), and the
SSRC is kept. Among the default codecs the audio clock rates differ (Opus 48000, G722/PCMU/PCMA
8000), so a mid-stream switch between them is a clock-rate switch.

## Gaps, in order of importance

1. **Receiver: clock rate per payload type (M).** RFC7160-4.3-1, with RFC 8834 4.3-5/-7. The
   receiver stream needs the payload-type to clock-rate map of the section, not one rate; jitter
   by the RFC 7160 formula; a test switching PCMU to Opus on one SSRC. The same map fixes the
   NACK/RTX and jitter-buffer assumptions after a payload type switch.
2. **Sender: a new SSRC per clock rate (M).** RFC7160-4.1-1, -2: when the codec an encoding is sent
   with changes to another clock rate, BYE the old SSRC, bind a new one, signal it
   (negotiation-needed for `a=ssrc`); or refuse the switch in `write_rtp` and document that the
   application must use a new encoding. Today's `rebind_local_streams` deliberately keeps the SSRC
   and sends no BYE, which is right for a same-rate change and wrong for this one.
3. **Multiple SRs after a switch (S).** RFC7160-4.1-3, and a test for 4.3-2.

## Bugs found

1. **Sender report timestamps go wrong when the application switches payload type across clock
   rates.** `rtc-interceptor/src/report/sender_stream.rs:101-103` extrapolates `rtp_time` with the
   clock rate bound for the stream. Reproduce: bind a local audio stream as Opus (48000), write
   PCMU packets (payload type 0, timestamps advancing 160 per 20 ms) on the same SSRC, fire the
   report timer 500 ms after the last packet and compare `rtp_time` with `last_ts + 4000`; the code
   gives `last_ts + 24000`.
2. **Receiver jitter is scaled by the wrong clock after a payload type switch.**
   `rtc-interceptor/src/report/receiver_stream.rs` (`process_rtp`). Reproduce: bind a remote stream
   as Opus, feed perfectly paced PCMU packets (160 ticks per 20 ms); the RR's jitter should stay 0
   and instead grows, since arrival time is converted at 48000 Hz.

## Status after the RTP wire work (`conf/rtp-wire`)

`rtc-rtp::clock_rate` holds the rules as tested helpers (SSRC per clock rate, the sender timestamp without RTCP, the receiver's difference with the earlier packet's clock rate). Using them in the sender and in the report interceptors is open (bugs 1 and 2).

## Status after the media work (`conf/media-18-clock-rate-ssrc`)

The sender follows section 4.1 by default: a packet written with a negotiated codec of another
clock rate moves its encoding to a new SSRC (bug 1 does not arise: each SSRC is bound with its own
clock rate), a return to a rate used before says BYE for the SSRC that used it, and the next
compound packet leads with the current rate's SR, the other rates' behind it.
`SettingEngineBuilder::with_ssrc_per_clock_rate(false)` keeps one SSRC (then bug 1 stands: the
sender report extrapolates with the bound clock rate). Bug 2 was fixed earlier (4.3-1). Open: 4.1-4
(RFC 6051, MAY).

# Clause audit: RFC 6762 (Multicast DNS)

Spec: RFC 6762, February 2013 (current; not obsoleted). Audited against fork master 8916bc3;
verdicts brought up to date with the responder and resolver work on `conf/mdns-rfc6762`.
Scope: what a host that publishes unique `<name>.local` address records and resolves such names
must do, the use draft-ietf-mmusic-mdns-ice-candidates makes of mDNS. Service discovery and
shared records are grouped into `n/a` rows per section. All sections 2 to 22 and Appendix C
were read; none skipped.

Code: `rtc-mdns/src/proto/` (`mod.rs`: `Mdns`, the sans-I/O connection; `resolver.rs`: query
series and the address cache; `responder.rs`: probing, announcing, answering, goodbyes;
`wire.rs`: the message reader and writer; `rate.rs`: the message budget and the jitter source),
`rtc-mdns/src/config.rs`, `rtc-mdns/src/socket.rs` (`MulticastSocket`, the one piece of I/O the
crate ships), `rtc-mdns/src/message/` (the DNS wire types; `Mdns` uses its name and header
decoding), `rtc-ice/src/agent/agent_proto.rs` (routing), `src/peer_connection/handler/demuxer.rs`.

Shape of the implementation: a name owns one address record and its NSEC companion. A name is
probed for unless it is `<uuid>.local`, announced twice, answered (multicast at most once a
second per record, unicast where asked), defended, sent back to probing on a conflict and
withdrawn with a goodbye. A query is two questions (A, AAAA), resent at doubling intervals until
the first answer or its timeout (30 s by default); answers are cached for their TTL in a cache of
at most 256 addresses. Every message sent draws on one token bucket. Timers and random delays
are driven by the instant the caller supplies and a seeded generator. "proc" rows carry no
RFC 2119 keyword.

Tests are in `rtc-mdns/src/proto/` (`mdns_responder_test.rs`, `mdns_resolver_test.rs`,
`wire_test.rs`, `mdns_test.rs`, `mdns_answer_trust_test.rs`) and `rtc-mdns/tests/`
(`audit_bugs.rs`, `integration_test.rs`).

## What is left, in order of importance

1. **Unicast awareness through the engine (S).** RFC6762-5.5-1, -5.5-2, -6-14. `Mdns` applies
   the unicast rules when the caller reports each datagram's destination address
   (`MdnsConfig::with_destination_reported`). `rtc-ice` and the peer connection do not: the
   driver has to read `IP_PKTINFO` and `rtc-ice` has to set the option. With it,
   MDNSICE-3.2.1-4 (`with_unicast_response`) can be turned on where the application owns
   port 5353.
2. **Defaults the agent has to switch (S).** RFC6762-5.2-5: `with_first_query_delay(true)` in
   `rtc-ice/src/mdns/mod.rs::create_multicast_dns`, and the three `rtc-ice` tests that expect a
   scheduled query in the same `handle_timeout` advance their clock by 120 ms.
   RFC6762-6.3-2: a design choice, see the row.
3. **Legacy queries through ICE (S).** RFC6762-6.7-1: `Agent::handle_read` hands `Mdns` only
   datagrams from port 5353.
4. **A lost name (S/M).** RFC6762-3-2: `rtc-ice` ignores `MdnsEvent::LocalNameConflict`; it
   should register another name for the address (the candidate already signalled cannot be
   renamed, so the new name serves later candidates and ICE restarts).
5. **On-link check (S).** RFC6762-11-2: the peer connection could pass the interface subnets
   (`with_on_link_subnets`); the default stays the address-scope check.
6. **Cache upkeep (M, SHOULD-level).** RFC6762-10.3 (sections 10.4, 10.5): reconfirmation
   queries and passive observation of failures.
7. **Optional (S/M, MAY).** RFC6762-3-4.

# RFC 7941: RTP Header Extension for the RTCP Source Description Items

Spec: RFC 7941, August 2016 (Proposed Standard). Audited against fork master 8916bc3. Sections done: 4.1 (4.1.1,
4.1.2), 4.2 (4.2.1 to 4.2.6), 5 (as features), 6. The use the engine makes of this RFC is the MID item
(`urn:ietf:params:rtp-hdrext:sdes:mid`, registered by RFC 8843) and the RID items of RFC 8852 (see rfc8852.md).

Code: reading `src/peer_connection/handler/interceptor.rs:911-966` (`get_rtp_header_extension_ids`), `:483-590`
(`bind_undeclared_ssrc`), `:682-900` (`bind_by_rid`); registration
`src/peer_connection/configuration/interceptor_registry.rs:400-425`; RTCP SDES
`rtci-rtcp/src/source_description/mod.rs`; header protection `src/peer_connection/cryptex.rs`.

The engine reads SDES header extensions and never writes one on a media packet: `RTCRtpSender::write_rtp`
(`src/rtp_transceiver/rtp_sender/mod.rs:402`) sends the header the application built. Every integration test that
needs MID or RID stamps it itself (`tests/simulcast_rtx_rrid.rs:305`, `tests/one_media_section_rtc_to_rtc_simulcast.rs:476`).

## Gaps, in order of importance

1. **Send MID (and RID) from the engine (M).** RFC7941-4.1-2, -4.2.3-1, -4.2.4-1, -4.2.4-2, -4.2.1-1. In
   `write_rtp` (or an interceptor at the sender end of the chain) stamp `sdes:mid`, and `rtp-stream-id` for a
   simulcast encoding, on the first N packets of each SSRC and after a change, until an RR for that SSRC arrives; pick
   the header form from the negotiated IDs. This is the feature RFC 8843 and RFC 8853 lean on.
2. **RTCP SDES items above 8 (S).** RFC7941-4.2.6-2 and bug S1: parse unknown item types by their length instead of
   ending the chunk; add MID (15), RtpStreamId (12), RepairedRtpStreamId (13).
3. **MID changes on a bound SSRC (S).** RFC7941-4.2.6-1: apply a new MID from a packet with a higher extended
   sequence number; ignore older ones.
4. **Header-extension confidentiality by default (decision).** RFC7941-6-1: either negotiate Cryptex by default (the
   W3C default is `negotiate`) or record the gap. Decided (cryptex-1): `setting`, not `conflict`. RFC 7941 section 6
   says "In RTP sessions where any type of confidentiality protection is enabled for RTCP, the SDES item header
   extensions MUST also be protected"; W3C webrtc-extensions 10.2 requires only the default value
   (`rtpHeaderEncryptionPolicy = "negotiate"`), and its sentence that under `negotiate` with a peer lacking Cryptex
   "RTP header extensions and CSRCs are sent in the clear" is in the "Enumeration description (non-normative)"
   table. Nothing normative in the W3C text has SDES items sent in the clear: a `negotiate` endpoint could meet RFC
   7941 by refusing or by not sending them. The texts can both be met; what keeps the default from the RFC form is
   a peer, the recorded Firefox 152 offer, which signals neither Cryptex nor RFC 6904 and names its layers only by
   RID in the clear. That is RULES.md's `setting` (the default differs because a named peer cannot interoperate),
   not `conflict` (a W3C text contradicting the clause for the same observable state).
5. **MTU budget for engine-added bytes (S).** RFC7941-4.2.2-1.
6. **Tests (S).** RFC7941-4.1.2-1 (MID in a two-byte header).

## Bugs found

- **S1. An RTCP SDES item of a type above 8 ends the chunk and desynchronises the packet.**
  `rtci-rtcp/src/source_description/mod.rs:80` (`_ => SdesType::SdesEnd`), `:263-269`, `:170-178`. Reproduce:
  unmarshal an SDES packet with one chunk `ssrc, CNAME(1) len 1 "a", MID(15) len 1 "0", END, padding`: the chunk
  stops at the MID type byte, and its length and text bytes are read as the start of a next chunk (or the packet fails
  with `PacketTooShort`). RFC 3550 6.5 has receivers skip unknown items by their length; RFC 8843 and RFC 8852 define
  items 15, 12 and 13. (Owned by rfc3550.md; recorded here because it is what blocks SDES MID and RID in RTCP.)
- **S2. MID demultiplexing depends on the RID extension being negotiated.**
  `src/peer_connection/handler/interceptor.rs:927-938`: `get_rtp_header_extension_ids` returns `None` when
  `sdes:rtp-stream-id` is not in the negotiated set, before it looks at the MID. Reproduce: two audio transceivers,
  a media engine with only `sdes:mid` registered, a remote description without `a=ssrc`; send a packet carrying MID
  for the second section: `bind_undeclared_ssrc` returns false and the packet finds no track.
- **S3. A MID or RID that is not valid UTF-8 becomes the empty string.** `handler/interceptor.rs:945-961`
  (`unwrap_or_default`). Harmless for RID; for MID it makes the packet look as if it had none. Reproduce: MID
  extension bytes `0xFF`.

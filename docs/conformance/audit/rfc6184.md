# RFC 6184: RTP Payload Format for H.264 Video

Spec: RFC 6184, May 2011 (obsoletes RFC 3984). Audited against fork master 8916bc3.

Scope: §5 (payload format), §6 (packetization rules), §7 (de-packetization), §8 (parameters and
SDP, as far as the engine matches fmtp lines and registers default codecs), §9, §10. The engine is
a transport: it has no encoder or decoder, so clauses that bind those are `n/a`. Informative
appendices (§12, §13) carry no requirements.

Level column: MUST covers MUST / MUST NOT / SHALL / REQUIRED and the descriptive "is set" rules of
§5.1; SHOULD covers SHOULD / SHOULD NOT / RECOMMENDED; MAY covers MAY / OPTIONAL features.

Abbreviations: `h264/mod.rs` = `rtci-rtp/src/codec/h264/mod.rs`; `fmtp/h264` =
`src/rtp_transceiver/fmtp/h264/mod.rs`; `rtp_codec.rs` =
`src/rtp_transceiver/rtp_sender/rtp_codec.rs`; `media_engine.rs` =
`src/peer_connection/configuration/media_engine.rs`; `packetizer` =
`rtci-rtp/src/packetizer/mod.rs`; `sample_builder` = `rtci-media/src/io/sample_builder/mod.rs`.

## Gaps, in order of importance

1. **H264-A (S): refuse what cannot be sent.** `H264Payloader::with_packetization_mode(2)` must
   not silently behave as mode 1 (RFC6184-6.4-2), and codec negotiation must not accept an H.264
   payload type on MIME type alone (RFC6184-8.2.2-1, 8.2.2-3). Make the H.264 fallback in
   `codec_parameters_fuzzy_search` / `update_from_remote_description` require a supported
   `packetization-mode` (0 or 1), and make `payloader()` return an error for mode 2.
2. **H264-B (S): fmtp defaults.** Absent `packetization-mode` equals 0 and absent
   `profile-level-id` equals `42000A` in `H264Fmtp::match_fmtp` (RFC6184-8.1-1, 8.1-3); range-check
   the mode (8.1-5). Two tests currently pin the wrong behaviour and must change.
3. **H264-C (M): profile matching per Table 5.** Compare profile_idc plus the profile-iop
   equivalence classes, and treat the Level-1b bit as level (RFC6184-8.1-6). Chrome's
   `H264ProfileLevelId` logic is the reference.
4. **H264-D (M): payloader order and aggregation.** Stop reordering parameter sets
   (RFC6184-5.5-2, 6.3-3), keep every SPS/PPS (Bugs 2, 3), compute the STAP-A header's F and NRI
   from the aggregated units (RFC6184-5.7-3, 5.7-4), copy F into the FU indicator (5.8-9), and
   aggregate other small NAL units of the access unit (5.7.1-1). Reject input NAL types 0 and
   24-31 (5.4-2, 5.8-5).
5. **H264-E (S): depacketizer edge cases.** Accept an empty FU payload (RFC6184-5.8-13), accept
   one-byte NAL units such as end-of-sequence (Bugs 5), ignore reserved types without failing the
   sample (5.4-3).
6. **H264-F (M): loss-aware FU reassembly and the missing tests.** Give `H264Packet` (or a wrapper
   used by `H26xWriter`) the sequence number so a lost middle fragment drops the NAL unit
   (RFC6184-5.8-14); add `SampleBuilder<H264Packet>` tests for reordering, marker / timestamp
   boundaries and gaps (5.1-2, 5.1-4, 5.6-2, 5.8-2, 5.8-3, 7.1-1).
7. **H264-G (L): interleaved mode.** STAP-B, MTAP16/24, FU-B, DON handling, the de-interleaving
   buffer and its SDP parameters (RFC6184-5.5-4..8, 5.7.1-3, 5.7.2-*, 5.8-6, 6.4-1, 7.2*, 8.1-10,
   8.2.2-9). No browser offers it; needed only for the literal 100%.

## Bugs found

1. **A mode-2 or unknown-profile H.264 payload type can be negotiated and is then sent as mode 1.**
   `media_engine.rs:1212-1214` falls back to partial (MIME-only) matches when nothing matched
   exactly; `rtp_codec.rs:189-199` produces them; `h264/mod.rs:77-82` maps mode 2 to mode 1.
   Reproduce: remote offer whose only video format is
   `a=fmtp:96 packetization-mode=2;profile-level-id=42e01f`; assert the answer rejects the m-line
   (today it accepts payload type 96), then that `payloader()` for the negotiated codec errors.
2. **Parameter sets are reordered.** `h264/mod.rs:174-180` stashes SPS and PPS and emits them only
   before the next other NAL unit once both are present. Reproduce: payload
   `SPS, SEI(0x06), PPS, IDR` in mode 1; output is `SEI, STAP-A, IDR`, not the input order.
3. **A second SPS or PPS in one access unit overwrites the first, which is never sent.**
   `h264/mod.rs:175, 178` keep one of each. Reproduce: payload `SPS, PPS(id 0), PPS(id 1), IDR`;
   only the second PPS appears in the STAP-A. Also: an access unit with an SPS but no PPS never
   sends the SPS until some later PPS arrives.
4. **An FU-A with an empty payload is refused.** `h264/mod.rs:357` returns `ErrShortPacket` for any
   two-byte packet that is not an AUD; RFC 6184 5.8 allows an empty FU payload. Reproduce:
   `depacketize(&[0x7c, 0x85])` (start), then a normal end fragment: the first call errors and the
   NAL unit is lost.
5. **One-byte NAL units are refused.** `h264/mod.rs:347` rejects `packet.len() <= 1`, so
   end-of-sequence (type 10) and end-of-stream (type 11), which are a header byte alone, error on
   receive, while the payloader sends them (`h264/mod.rs:129`). Reproduce:
   `depacketize(&[0x0a])` returns `ErrShortPacket`. Two-byte NAL units other than AUD fail the
   same way at line 357.
6. **The STAP-A header ignores the units it carries** (`h264/mod.rs:65`): F=0, NRI=3 always.
   Reproduce: SPS `0x27 ..`, PPS `0x28 ..` (NRI 1): expected header `0x38`, got `0x78`.
   `test_h264_payloader_payload_sps_and_pps_handling` asserts the wrong value for NRI-0 input.
7. **A lost middle FU-A fragment yields a spliced NAL unit** when `H264Packet` is fed directly (as
   `H26xWriter::write_h264` does, `rtci-media/src/io/h26x_writer/mod.rs:130-133`). Reproduce:
   fragment a NAL unit into four FU-As, feed 1, 2 and 4: a NAL unit missing the third chunk is
   returned as if whole.

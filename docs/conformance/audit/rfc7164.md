# RFC 7164: RTP and Leap Seconds

Spec: RFC 7164, March 2014 (Standards Track, updates RFC 3550). Audited against fork master
8916bc3. Sections covered: 5 (all normative text). Referenced by RFC 8834 4.10.

How the engine stands: NTP timestamps in SR and XR RRTR come from a wall-clock baseline taken once
(`SystemInstant::now(now)`, `report/sender_stream.rs`, `report/receiver.rs:254`) and advanced by
the monotonic `Instant` the application passes in. Nothing in the tree mentions leap seconds. A
baseline plus a monotonic clock does not jump at a leap second, which avoids a discontinuity inside
a session; it also means the timestamps are off by one second from UTC afterwards, and a session
that starts inside the leap second takes whatever the OS clock says.

## Gaps, in order of importance

1. **Leap-second guard in the report interceptors (S).** RFC7164-5-1, 5-3, 5.1-1 to -5: a helper
   "is this NTP time within the last second of a month, plus or minus one second"; the sender
   report interceptor sends an RR (or skips the NTP/RTP pair) inside that window; the receiver
   ignores the NTP/RTP mapping of an SR whose timestamp falls in it (LSR/DLSR echo is unaffected,
   only synchronisation use). Tests drive the deterministic clock across 23:59:59 on a month end.

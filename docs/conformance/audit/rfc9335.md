## Gaps, in order of importance

1. **End-to-end test that negotiation reaches the wire (S)** — 4-3, 4-5, 4-6, 5.2-2. Two peers with
   `Negotiate`: assert sent RTP with a mid extension carries 0xC0DE and decrypts; with one peer on
   `Disable`: assert 0xBEDE and normal reception; renegotiate from one state to the other. Today the
   link `cryptex_negotiated()` -> `SrtpHandlerContext::set_cryptex` -> contexts created by a later DTLS
   handshake (`handler/srtp.rs:204-214`) has no test.
2. **Stream-level error under `Require` (S)** — 5.2-3. A refused packet is one `Error::Other` among
   others; surface a typed error / event so an application can tell the peer is violating the policy.
3. **Clear fallbacks are silent (S)** — 5-2, 5.1-1. With Cryptex negotiated (or required), a packet whose
   extension profile is not 0xBEDE / 0x1000 (two-byte with appbits, RFC 3550 profile-specific extension)
   is sent with its header in the clear. Under `Require` the sender should refuse it; add tests for both
   profiles and for a padded packet (6.2-1).
4. **Per-packet / per-sender choice (S, optional)** — 4-2.
5. **Default policy (S, decision)** — W3C default is `negotiate`; the engine defaults to `Disable`.
   Already documented in FORK.md; listed for completeness.
6. **TRANSPORT mux category (S)** — 9.1-1. Accept `a=cryptex` taken from the bundle-tag section only if
   strictness against real peers ever shows up as a failure; current behaviour fails closed (no Cryptex).
7. **Coexistence with RFC 6904 (depends on RFC 6904)** — 5-3.

## Bugs found

- **Header extensions leave in the clear under `Require` for non-RFC-8285 or appbits profiles**
  (`rtc-srtp/src/cryptex.rs:107-112`, `rtc-srtp/src/context/srtp.rs:139-149`). Reproduction: context with
  `Cryptex { send: true, require: true }`, encrypt an RTP packet with X=1 and extension profile `0x1001`
  (two-byte, appbits 1) or `0xABCD`: the call succeeds and the output has the extension bytes unchanged.
  Expected under `Require`: an error (the receiving side of the same policy would refuse this packet).
  Severity low: the engine's own packetizer only emits 0xBEDE / 0x1000.
- No decryption or signalling defect found; the RFC's Appendix A vectors are reproduced in both
  directions for AES-CM and AES-GCM.

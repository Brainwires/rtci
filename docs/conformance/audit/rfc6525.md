# RFC 6525: SCTP Stream Reconfiguration

Spec: RFC 6525, February 2012 (Proposed Standard). Audited against fork master 8916bc3 (`docs/conformance-audit` worktree), read-only.

RFC 6525, Stream Control Transmission Protocol (SCTP) Stream Reconfiguration, February 2012. The engine
implements one of its five operations: the Outgoing SSN Reset Request and its response, which is what
closing a WebRTC data channel uses (RFC 8831 6.7). Incoming SSN Reset, SSN/TSN Reset and Add Streams
are not implemented, and a RE-CONFIG carrying one of them is not answered: the packet that carries it
fails to parse and is dropped whole. Within the implemented operation the one-request-in-flight rule,
the sequence-number checks and the retransmission of the answering reset are not followed.

Totals (81 clauses):

- `MUST: tested 23 / untested 8 / partial 9 / missing 19 / violated 4 / n-a 0`
- `SHOULD: tested 0 / untested 1 / partial 0 / missing 10 / violated 0 / n-a 1`

lower case ("must", field definitions); SHOULD covers SHOULD / SHOULD NOT / RECOMMENDED; MAY covers

## Gaps, in order of importance

1. **Retransmit and time every request, and never give one up silently (S).** Start the
   Re-configuration Timer for the request sent in answer to a peer's reset; restart it on In progress
   without counting; when the retransmission limit is passed either end the association or keep
   retransmitting at RTO.max. Closes RFC6525-5.1.1-6, 5.1.1-9 (test), 5.1.1-10, 5.2.7-2, 5.2.7-3.
2. **Answer every request parameter (M).** Parse types 14, 15, 17, 18 (at least far enough to read
   the request sequence number) and answer Denied; an unknown parameter stops that chunk only, not
   the packet. Closes 4-1, 4.2-1, 4.3-1, 4.5-1, 4.5-2, 4.6-1, 4.6-2 (parsing), 5.2.1-5, and the response
   half of 5.2.3-1, 5.2.4-6, 5.2.5-1, 5.2.6-1.
3. **Empty stream list means all streams (S).** Closes 5.2.2-4.
4. **Request sequence numbers (M).** Track the peer's next expected request number; answer Bad
   Sequence Number for a wrong one and repeat the stored answer for the last one; fill the Response
   Sequence Number field of own requests. Closes 5.1.2-7, 5.2.1-4, 5.2.1-6, 5.1.7-1 (test), 5.1.7-2
   (more of Table 3), 5.1.2-2 (test).
5. **One request in flight, one chunk per answer (M).** Queue further resets while a request is
   outstanding and merge their stream lists; send Response + Outgoing SSN Reset Request as one chunk;
   bundle a SACK. Closes 5.1.1-5, 5.2.1-2, 5.2.1-3, 5.1.2-9, and 5.2.1-1 (test).
6. **Deferred reset holds later data; SSNs stop while a reset is pending (M).** Hold DATA beyond
   Sender's Last Assigned TSN on streams with a pending reset and release it into the fresh stream
   state; on the sending side assign SSNs when a message leaves the queue (or queue writes) while a
   reset of that stream is outstanding. Closes 5.2.2-3, 5.2.2-6, 5.1.2-1, 5.2.7-5.
7. **Honour the negotiation (S).** Record whether the peer listed chunk 130; fail `Stream::stop` /

## Bugs found

1. **The reset this side sends in answer to a peer's reset is never retransmitted**
   (`association/mod.rs:2457-2474` stores it in `reconfigs` but the only `Timer::Reconfig` start is
   at `:2822-2825`, on the application-initiated path). If that one packet is lost the peer's data
   channel stays in `closing` for good and the entry stays in `reconfigs`; 64 such losses stop all
   further answering resets (`MAX_OUTSTANDING_RECONFIGS`). Reproduce: `Link` with a filter that drops
   the first server-to-client datagram whose first chunk is RE-CONFIG holding parameter 13; client
   calls `stream.close(now)`; run 60 s; assert the client saw `AssociationLost { reason: Reset }` for
   the stream and `server.conn().reconfigs.is_empty()`.
2. **An Outgoing SSN Reset Request with an empty stream list resets nothing and is answered
   "Success - Performed"** (`association/mod.rs:2381-2410`). The peer then sends SSN 0, which
   `ReassemblyQueue::push` drops as stale while the TSN is acknowledged: silent loss of every ordered
   message until the SSN catches up. Reproduce: deliver two ordered messages on stream 1, then
   `handle_reconfig(&reset_request_chunk(7, a.peer_last_tsn, vec![]))`, then a DATA chunk with SSN 0
   on stream 1; assert it is readable.
3. **A RE-CONFIG with a parameter the engine does not parse (14, 15, 17, 18) takes the whole packet
   with it** (`param/mod.rs:74-78` -> `chunk/chunk_reconfig.rs:69-77` -> `packet.rs:149` ->
   `association/mod.rs:624-629`). Bundled DATA is lost and retransmitted, and the peer's request is
   retransmitted until its limit with no answer. Reproduce: packet = DATA(tsn) + RE-CONFIG(Incoming
   SSN Reset Request); assert the DATA is delivered and a response with Result Denied goes out.
4. **A reset request is given up silently after five timer expiries**
   (`association/timer.rs:41`, `:160-164`; `association/mod.rs:590-591` does not re-arm the timer and
   `:3900` ignores the failure). The count also runs while the peer answers In progress, which this
   engine itself does until its application drains the stream. Reproduce: `stream.close(now)`, answer
   every retransmission with `response(rsn, ReconfigResult::InProgress)`, call `handle_timeout` at
   each `poll_timeout`; after the sixth expiry `a.timers.get(Timer::Reconfig)` is `None` while
   `a.reconfigs` still holds the request.
5. **Data written after `Stream::stop` uses the old SSN sequence and is sent before the response**
   (`association/stream.rs:292-309`, `:602-617`). The peer has reset to SSN 0 and holds that data
   back for good. Reproduce: in `reset_after_two_messages` write a third message after `stop` and
   before the response; its DATA chunk carries SSN 2.
6. **A request sequence number older than the last 64 is performed again**
   (`association/mod.rs:1933-1955`, `:2419-2423`). A late duplicate resets a stream that has since
   been reused. Reproduce: send requests 0..=64 for stream 4, open stream 4 again and deliver data,
   replay request 0; the stream is unregistered a second time.
7. **Data of the stream's next use that arrives while a reset is deferred is lost**
   (`association/mod.rs:1459-1546`, no hold for TSNs beyond Sender's Last Assigned TSN). Only a peer
   that breaks step A1 sends such data (this engine does, after `Stream::stop`, bug 5). Reproduce:
   deliver RE-CONFIG(reset stream 1, last TSN = T) while TSN T is missing, then DATA(T+1, stream 1,
   SSN 0), then DATA(T); assert the message with TSN T+1 is readable after the reset.

# RFC 5124: Extended Secure RTP Profile for RTCP-Based Feedback (RTP/SAVPF)

Spec: RFC 5124, February 2008. Audited against fork master 8916bc3. Scope: sections 2 (combining AVPF
and SAVP), 3.1-3.3.1 (profile identification and offer/answer), 4 (interworking), 5 (security). RTSP
(3.3.2), SAP/announcements (3.3.3) and the RFC 4567/4568 key-management attributes are `n/a`: the
engine keys SRTP with DTLS-SRTP only and has no RTSP or SAP. The SRTP/SRTCP transforms themselves are
audited under RFC 3711 (area `ice-dtls-srtp`); this file covers only what SAVPF adds.

Where it lives: `src/peer_connection/handler/srtp.rs` (every RTCP packet is marshalled and passed to
`Context::encrypt_rtcp`, every inbound one through `decrypt_rtcp`), `src/peer_connection/sdp/mod.rs`
(the `m=` proto is always written `UDP/TLS/RTP/SAVPF`; the remote `m=` proto is never read).

## Gaps, in order of importance

1. **Remote profile is never inspected (S).** ID 3.3.1-6. Read the offered `m=` proto: accept the
   JSEP-equivalent strings (`UDP/TLS/RTP/SAVPF`, `TCP/DTLS/RTP/SAVPF`, and the legacy `RTP/SAVPF`,
   `RTP/SAVP`, `RTP/AVPF`, `RTP/AVP` that RFC 8829 5.1.2 lists, when a fingerprint is present), echo
   the offered string in the answer as JSEP requires, and reject anything else with port 0. Add the
   test that offers `RTP/AVP` without a fingerprint and expects rejection.
2. **SRTCP overhead in RTCP timing (S, after the RFC 4585 scheduler).** IDs 2-2, 2.3-1. When
   `avg_rtcp_size` exists, measure the protected datagram, not the plain compound packet.
3. **Tests (S).** IDs 2-1, 3.1-1, 5-2.

## Bugs found

1. **A non-SAVPF offer is accepted and answered as SAVPF.** `src/peer_connection/sdp/mod.rs`: the
   answer builder writes `UDP/TLS/RTP/SAVPF` for every live section and nothing compares it with the
   offer. Reproduce: `set_remote_description` with a browser offer whose video line is rewritten to
   `m=video 9 RTP/AVP 96` (fingerprint and ICE left in place), `create_answer`; the answer's line reads
   `m=video 9 UDP/TLS/RTP/SAVPF 96`, where JSEP expects the offered string echoed and RFC 5124 3.3.1
   expects a rejection. Whether to echo or reject is the JSEP auditor's call; today it does neither.

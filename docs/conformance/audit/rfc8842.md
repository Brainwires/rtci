## Gaps, in order of importance

1. **Answer must keep the negotiated DTLS role (S).** RFC8842-5.3-6, violated. `create_answer`
   has to prefer the established role (`dtls_transport().role()` once the transport is started and
   not closed) over `answering_dtls_role` and the default. Add an rtc2rtc test where the original
   offerer answers a re-offer.
2. **Read `a=setup` at session level (S).** RFC8842-5.3-10: `RTCDtlsRole::from(&SessionDescription)`
   only walks media sections.
3. **`tls-id` (M).** RFC8842-3.1-3, 3.2-1, 3.3-1, 4-1..4-4, 4-7, 5.2-3, 5.3-3, 5.3-5, 5.5-1/2:
   generate a 120-bit value per association, write it on the BUNDLE-tag section (only in answers
   to offers that carry one), keep it across renegotiation, change it with a new association,
   and treat a changed remote value as a request for one. No browser sends it today, so it must
   stay optional on receipt.
4. **New association on a fingerprint or role change without ICE restart (M).** RFC8842-3.1-1/2,
   4-5: decide and implement: either refuse such a description (the peer broke §6: a new
   association needs new ICE candidates) or restart DTLS. Today it is silently ignored.
5. **3-tuple for a new association (M).** RFC8842-5.1-1/2, 6-2: when DTLS is restarted, force the
   ICE restart to regather (as `discard_local_candidates_during_ice_restart` does), or keep the
   old endpoint alive until the new handshake completes (5.5-3) so stray old records cannot hit
   the new association.
6. **ClientHello before the answer (M).** RFC8842-5.2-4: start the ICE agent and a passive DTLS
   endpoint when the local offer is set; today recovery depends on the peer's retransmission.
7. **Tests (S).** Offer carries `actpass` (5.2-1); no `tls-id` in the answer (5.3-8).
8. **More fingerprint hash functions (S).** RFC8842-5.1-6, with RFC 8122.

## Bugs found

- **The answer to a re-offer flips the DTLS role** (`src/peer_connection/mod.rs:1036-1070`).
  A offers, B answers `active` (B client, A server). Later B sends a new offer (`actpass`); A's
  `create_answer` ignores its established role and writes `a=setup:active`. RFC 8842 §5.3 forbids
  the change; libwebrtc refuses such an answer ("Failed to set SSL role for the transport").
  Reproduce: rtc2rtc, connect with A as offerer, then have B `create_offer` and A
  `create_answer`; assert A's second answer contains `a=setup:passive`. With an ICE restart in
  that second exchange the engine also tears its own healthy DTLS session down, because
  `derive_role` now differs from `dtls_role` (`transport/dtls/mod.rs:365-376`).
- **Session-level `a=setup` is ignored** (`src/peer_connection/transport/dtls/role.rs:148-167`).
  Reproduce: `RTCDtlsRole::from` on an SDP with `a=setup:passive` before the first `m=` line
  returns `Auto`; an offerer then derives `Server` from its ICE role while the peer is passive
  too, and no ClientHello is ever sent. Extend `test_dtls_role_from_remote_sdp` with that case.
- **A changed remote fingerprint without an ICE restart is silently kept out**
  (`src/peer_connection/mod.rs:1736-1760`): the description is accepted, the old fingerprint
  stays in force. Reproduce: apply a second remote description identical but for the
  `a=fingerprint` value; `dtls_transport.remote_dtls_parameters` is unchanged and no error is
  returned.
- **`setup:holdconn` is accepted as "no preference"** (`role.rs:157`). Reproduce: remote answer
  with `a=setup:holdconn`; the offerer picks a role from its ICE role instead of refusing the
  description.

## Status after `conf/dtls-sdp-1`

The table above carries the verdicts after that change; the two sections before this one are the
audit's findings at 8916bc3, kept for the record.

- Gaps 1 to 4, 7 and 8 are closed (rows 3.1-1 to 3.1-3, 3.2-1, 3.3-1, 4-1 to 4-5, 4-7, 4-8,
  5.1-5, 5.1-6, 5.2-1, 5.2-3, 5.2-5, 5.3-3, 5.3-5, 5.3-6, 5.3-8, 5.3-10, 5.5-1, 5.5-2).
- All four bugs are fixed, each with a test that failed before: the role flip
  (`tests/dtls_association_roles.rs`), the ignored session-level `a=setup` and the accepted
  `holdconn` (`tests/dtls_sdp_attributes.rs`), the ignored fingerprint change
  (`tests/dtls_association_new.rs`).
- Open: gap 5 (a new 3-tuple for a new association: 5.1-1, 5.1-2, 5.1-3, 6-2; the engine has
  no sockets, the application chooses the candidates), gap 6 (a ClientHello before the answer:
  5.2-4, with RFC8122-6.2-6) and the SHOULD 5.5-3 (old and new association side by side).

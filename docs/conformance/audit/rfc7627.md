## Status of the gaps and bugs

The rows above carry the current verdicts; the lists below are the audit as it was made at 8916bc3.

- Fixed: gap 2 (no key export without the extension), with the crate-level bug under "Bugs found". The alerts for a missing extension are handshake_failure, as section 5.2 names.

## Gaps, in order of importance

1. **Known-answer test for the extended master secret (S).** RFC7627-4-2. One vector (premaster,
   session hash, expected master secret) pins the label and the 48-byte length; today a typo in the
   label would pass every test.
2. **Refuse key export without the extension (S).** RFC7627-5.4-1. `State::export_keying_material`
   returns an error when `extended_master_secret` is false, so DTLS-SRTP keys can never come from a
   legacy master secret whatever policy a crate user picks.
3. Nothing else: the abbreviated-handshake rules (5.3) bind only if session resumption is added.

## Bugs found

None in the engine's configuration. At crate level, `ExtendedMasterSecretType::Request` or
`Disable` followed by `export_keying_material("EXTRACTOR-dtls_srtp", ..)` exports from a legacy
master secret (RFC 7627 5.4). Reproduction: build both ends with `Disable`, complete the handshake,
call `export_keying_material`; it returns keys instead of an error.

# RFC 9429: JavaScript Session Establishment Protocol (JSEP): clause audit

Spec: RFC 9429, April 2024 (obsoletes RFC 8829; the code's comments still cite RFC 8829 and
draft-ietf-rtcweb-jsep-24 in places). Audited at fork master 8916bc3. Scope: sections 3 to 8; section 7
(examples) and the appendices carry no clause. The engine is the layer under a W3C-style API, so
promise / event-loop wording is read as "the call returns the error / emits the event".

Path legend: `pc/` = `src/peer_connection/`, `sdp/mod.rs` = `src/peer_connection/sdp/mod.rs`,
`me.rs` = `src/peer_connection/configuration/media_engine.rs`, `rtc-sdp/` = `rtc-sdp/src/`.
Lower-case requirements that describe required SDP content (the attribute lists of 5.2.1 and 5.3.1, the
checks of 5.8 to 5.11) are listed at MUST level. A verdict of `tested` names a test whose assertion I
read or whose flow cannot pass without the behaviour; everything else implemented is `untested`.

## Bugs found

- **RFC9429-5.2.2-1 / 5.3.2-1: session-version does not increment.** `update_sdp_origin`
  (`src/peer_connection/sdp/mod.rs:2359`) does `d.origin.session_version += 1` on a description whose
  version is the clock's sub-second nanoseconds. Reproduce: `create_offer` twice on one connection,
  parse both `o=` lines, assert `v2 == v1 + 1`; today v2 is unrelated to v1 and may be lower. (Also: a
  first version of 0 is taken as "not stored yet".)
- **RFC9429-5.3.1-31: the answer's bundle group is the first `a=group` of any semantics.**
  `generate_matched_sdp` (`src/peer_connection/internal.rs:597`) uses `attribute("group")`. Reproduce:
  offer with `a=group:LS 0 1` then `a=group:BUNDLE 0 1 2`; the answer has `m=... 0` for mid 2 and
  `a=group:BUNDLE 0 1`.
- **RFC9429-5.3.1-30: an offer with no `a=group` is answered with port 0 in every section.**
  `match_bundle_group` becomes `Some("")` (`internal.rs:599`) and `populate_sdp` zeroes each port
  (`sdp/mod.rs:1578`) while keeping the section's attributes. Reproduce: a one-section audio offer
  without `a=group:BUNDLE`; assert the answer's m= port is 9.
- **RFC9429-5.3.2-7: the answer's `a=setup` ignores the live DTLS association.** `create_answer`
  (`src/peer_connection/mod.rs:1036`). Reproduce: A offers, B answers `active` (A is DTLS server); B
  re-offers `actpass`; A's answer says `setup:active`. libwebrtc refuses a role change without an ICE
  restart.
- **RFC9429-5.8.1-12: session-level `a=setup` is not read.** `RTCDtlsRole::from(&SessionDescription)`
  (`src/peer_connection/transport/dtls/role.rs:148`) scans media sections only (and takes the first one
  that has the attribute, rejected or not). Reproduce: remote answer with `a=setup:active` at session
  level; the role resolves to `Auto`.
- **RFC9429-5.8.2-22: `a=msid` without appdata is dropped, and only the last msid line is kept.**
  `track_details_from_sdp` (`sdp/mod.rs:471`). Reproduce: offer with `a=msid:stream1` and no `a=ssrc`;
  no remote track is created. With `a=msid:s1 t` and `a=msid:s2 t` the track reports only `s2`.
- **RFC9429-5.10-1: a remote description that fails the ICE / fingerprint checks is half applied.**
  `set_remote_description` (`src/peer_connection/mod.rs:1452` then `1709`, `1727`). Reproduce: in
  stable, apply an offer with an m= section and no `a=fingerprint`; the call errors, yet
  `signaling_state()` is `have-remote-offer` and a transceiver exists.
- **RFC9429-5.1.2-6: legacy `m=application 9 DTLS/SCTP 5000` + `a=sctpmap` is treated as RTP.**
  `is_webrtc_datachannel` (`sdp/mod.rs:1933`) makes `get_application_media_section_sctp_port`'s
  `sctpmap` branch unreachable. Reproduce: such an offer; the answer rejects the section and a
  transceiver of kind application appears.
- **RFC9429-4.1.19-1: a remote candidate with neither mid nor m= index is accepted.**
  `add_remote_candidate` (`src/peer_connection/mod.rs:2007`).
- **RFC9429-5.2.2-30: `create_offer` works in any signaling state** (`src/peer_connection/mod.rs:814`),
  including have-remote-offer and the pranswer states, and assigns mids while doing so.

# RFC 6679: Explicit Congestion Notification (ECN) for RTP over UDP

Spec: RFC 6679, August 2012 (Standards Track). Audited against `conf/media-9-ecn` (on master
278aa571 with the media-5 to media-8 branches). Sections done: 3.2, 4, 5, 6, 7, 8, 10.1 (all
normative text an endpoint can meet; section 8 binds translators and mixers). Referenced by RFC
8888 section 7 ("the guidelines in Section 7.2 of [RFC6679] MUST be followed") and RFC 8834
section 7 (ECN for WebRTC endpoints).

Scope of the code. Wire codecs: `rtc-rtcp/src/transport_feedbacks/ecn_feedback/mod.rs` (RTCP ECN
Feedback packet, RTPFB FMT 8), `rtc-rtcp/src/extended_report/ecn.rs` (XR ECN Summary Report, BT
13). Receiver side: `rtc-interceptor/src/rtcp_session/{mod,ecn}.rs` (counts each remote source's
ECN field values from `TransportContext::ecn` on read, writes the feedback packet early and the
summary in every regular compound packet); RFC 8888 reports carry the per-packet marks
(`rtc-interceptor/src/rfc8888/`). Sender side: `rtc-interceptor/src/rfc8888/ecn.rs`
(`EcnValidation`: initiation, ongoing use and failure detection, fed per packet by RFC 8888 reports
or by RFC 6679 counters), `src/statistics/accumulator/{mod,rtcp_reports}.rs` (which streams mark,
`TransportContext::ecn` on write), `rtc-interceptor/src/cc/interceptor.rs` and
`rtc-interceptor/src/gcc/estimator.rs` (CE marks to the congestion controller). The ECN field
itself is the application's socket layer's (`SettingEngineBuilder::with_ecn`); the engine is
sans-I/O.

Negotiation (SDP) is the JSEP layer's: `a=ecn-capable-rtp` is written and read on
`conf/jsep-36-train-fixes` (not in this branch), which gates marking on it. What the engine takes
from a stream's negotiated feedback here: `nack ecn` (`RTCP_FB_NACK_ECN`) and an `xr` entry
`ecn-sum` (`RTCP_FB_XR`, `RTCP_XR_ECN_SUMMARY`), the form `a=rtcp-xr` formats reach a `StreamInfo`
in. The SDP rows below stay `missing` in this file until that branch is merged and they are
re-verified against it.

What the engine relies on from RFC 3168 (not audited as clauses here: its normative text binds
routers, TCP and the IP layer). Section 5: the two-bit ECN field with Not-ECT `00`, ECT(1) `01`,
ECT(0) `10` and CE `11` (`shared::EcnCodepoint`), set by the sender and changed only to CE by a
congested router; a CE mark is a congestion signal equal to a loss (section 5, "the same as a
dropped packet"), which is how `Gcc::on_reports` and `BandwidthEstimator::on_congestion_marks`
take it. Section 5.3: an ECT packet that is fragmented keeps its field in each fragment; the engine
keeps RTP packets under the MTU, so it sends none. Section 6.1.1.1's middlebox failures (a path
that clears or drops ECT) are what RFC 6679 section 7.2's validation detects. The engine never
reads or writes the IP header itself: the application's socket layer applies
`TransportContext::ecn` on each datagram (sans-I/O) and reports the received one.

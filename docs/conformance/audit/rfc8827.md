# RFC 8827 conformance audit: WebRTC security architecture

Spec: RFC 8827, January 2021. Audited at fork master 8916bc3. The engine is the layer under a
browser's JS API: clauses about origins, permission prompts and browser chrome (§6.1, §6.2, the UI
parts of §6.5) and about the IdP proxy that runs in a browser context (§7, §8) do not bind it and
are listed once each as n/a. What binds it: the SDP side of identity (§5), communications consent
(§6.3), IP location privacy mechanisms (§6.4), communications security (§6.5). Code read:
`src/peer_connection/transport/dtls/`, `src/peer_connection/handler/{dtls,srtp,ice}.rs`,
`src/peer_connection/certificate/`, `src/peer_connection/configuration/`, `rtc-dtls/src/conn/mod.rs`,
`rtc-dtls/src/cipher_suite/mod.rs`, `rtc-dtls/src/extension/extension_use_srtp.rs`. ICE-level
clauses are cross-references: the ICE audit owns their detail. All sections done.

## Gaps, in order of importance

1. **no_renegotiation (S).** RFC8827-6.5-16: answer a post-handshake ClientHello (server) or
   HelloRequest (client) with a warning-level no_renegotiation alert, rate-limited, and test that
   the association stays up (also closes 6.5-15's missing test).
2. **MKI from the server (S).** RFC8827-6.5-9: abort when ServerHello's `use_srtp` carries an MKI
   (same work as RFC 5764 gap 3).
3. **Negative tests for what holds by construction (S).** 6.3-2 (nothing but STUN before a pair is
   selected), 6.5-5 (no plain RTP; also remove or guard the `RTPMessage::Raw` write bypass),
   6.5-6 (NULL suites / profiles refused), 6.5-8 (`a=crypto` ignored), 6.5-13, 6.5-17,
   6.5-18 (two connections, two fingerprints), 6.5-21.
4. **Related-address suppression (S).** RFC8827-6.4-3: an option that writes `raddr 0.0.0.0 rport 0`
   (or omits them) on relay candidates under the relay policy.
5. **`a=identity` (L, likely "not implemented, on purpose").** RFC8827-5-*, 7.4-*: carrying the
   attribute, binding it to the fingerprints and hooking an application-supplied verifier. No
   browser ships it by default; it should be added to the "Not implemented, on purpose" table if
   the owner agrees, and still counts as missing.
6. **Application-set ICE credentials (decision).** RFC8827-6.3-4 is violated on purpose; record it
   in `docs/conformance.md` as a deliberate deviation.

## Bugs found

- **Renegotiation attempts get no alert** (`rtc-dtls/src/conn/mod.rs:825-835`). Reproduce: after
  `completed_pair()` in `conn_ported_test.rs`, encrypt and feed the server a fresh ClientHello at
  epoch 1; nothing is transmitted in reply. Expected: a no_renegotiation warning alert.
- **`RTPMessage::Raw` written into the pipeline leaves unencrypted**
  (`src/peer_connection/handler/srtp.rs:170-174`). Not reachable from the public API today.
  Reproduce: call `SrtpHandler::handle_write` with `RTCMessageInternal::Rtp(RTPMessage::Raw(..))`
  and observe the same bytes in `poll_write`. A debug assertion or an error would make the
  "no plain RTP" property structural.

## Status after `conf/dtls-sdp-1`

The table above carries the verdicts after that change for the rows of `src/peer_connection`.

- Gap 3: tests added for 6.3-2, 6.4-1, 6.5-5 (the `RTPMessage::Raw` bypass is now an error),
  6.5-7, 6.5-8, 6.5-18.
- Gap 5 (`a=identity`): the attribute is carried (5-1, 5-2, 5.1.4-1:
  `RTCPeerConnection::set_identity_assertion`, `remote_identity_assertion`). What is left is a
  work package of size L: a verifier hook that `set_remote_description` waits on (5.1.3-1),
  the identity kept per DTLS association and dropped when the fingerprints change (5.1.4-2,
  -3, -5), and the check that the certificate in use is one the assertion covers (7.4-1,
  7.4-2). Making and verifying an assertion needs an IdP proxy, which an engine does not have.
- Open elsewhere: `rtc-dtls` (6.5-9, 6.5-13, 6.5-15, 6.5-16, 6.5-17), `rtc-ice` (6.3-3, 6.4-3),
  and the decisions 6.3-4 and 6.5-21.

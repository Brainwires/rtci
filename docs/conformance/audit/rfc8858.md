# RFC 8858: Indicating Exclusive Support of RTP and RTCP Multiplexing Using SDP: clause audit

Spec: RFC 8858, January 2021 (updates RFC 5761). Audited at fork master 8916bc3.

The engine only ever multiplexes RTP and RTCP: it writes `a=rtcp-mux` in every RTP m= section and has no
separate RTCP component. It is, in the RFC's terms, an endpoint with exclusive support, but it never
says so: `a=rtcp-mux-only` is neither written nor read, and the peer's `a=rtcp-mux` is not read either.
A grep of `src/` and `rtc-sdp/src/` for `rtcp-mux-only` has no hit.

Path legend: `sdp/mod.rs` = `src/peer_connection/sdp/mod.rs`, `pc/` = `src/peer_connection/`.

## Gaps, in order of importance

1. **Honour the answer (S).** RFC8858-4.4-2, 4.5-5, 5.2-1, 5.2-2: read `a=rtcp-mux` from the remote
   answer; without it, stop the transceiver (and renegotiate with port zero) or fail the description.
2. **Say what the engine is (S).** RFC8858-4.2-1, 3-2, 4.5-1, 4.5-4: write `a=rtcp-mux-only` in offers
   (JSEP requires it under the `require` policy, rfc9429.md 5.2.1-47).
3. **No RTCP candidates (S).** RFC8858-5.3-2: drop the component-2 copies in `add_candidates_to_media_descriptions`.
4. **Tests.** An offer with `a=rtcp-mux-only` is answered with `a=rtcp-mux` and without `rtcp-mux-only`
   (RFC8858-4.3-1, 4.3-3).

## Bugs found

- **RFC8858-4.4-2 / 5.2-1:** a remote answer without `a=rtcp-mux` is accepted and RTCP is still sent on
  the RTP transport. Reproduce: offer from the engine, answer text with the `a=rtcp-mux` line removed;
  `set_remote_description` succeeds and the sender's RTCP goes out multiplexed.
- **RFC8858-5.3-2:** local descriptions list every candidate twice, as component 1 and component 2
  (`src/peer_connection/sdp/mod.rs:792`), for an endpoint that cannot receive RTCP on a second component.
  Reproduce: add one host candidate, read `local_description()`, count `a=candidate` lines (2).

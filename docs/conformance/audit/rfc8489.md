# RFC 8489 conformance audit: Session Traversal Utilities for NAT (STUN)

Spec: RFC 8489, February 2020 (obsoletes RFC 5389). Audited at fork master `8916bc3`.

Scope: the STUN layer the engine uses as a client and agent: `rtc-stun/` (message codec,
attributes, `Client`, `Agent`), the Binding server role an ICE agent plays
(`rtc-ice/src/agent/mod.rs`, `agent_selector.rs`), the long-term credential client in
`rtc-turn/src/client/`, and STUN / TURN URI parsing (`rtc-stun/src/uri.rs`,
`rtc-ice/src/url/mod.rs`). ICE-specific rules (pacing, RTO formula of RFC 8445 §14.3, 487) are
in `rfc8445.md`; TURN methods are in `rfc8656.md`.

Updated on branch `conf/stun-rfc8489`, which brings `rtc-stun` to RFC 8489: the codec limits
and receive checks, MESSAGE-INTEGRITY-SHA256, USERHASH, PASSWORD-ALGORITHM(S), ALTERNATE-DOMAIN,
OpaqueString, the nonce cookie with bid-down protection, the long-term credential rules, the
300 (Try Alternate) data, the retransmission timer of section 6.2, and a validated-message API
(`rtc_stun::validated`) that shows a receiver only the attributes its integrity check covers.
The rows below say `partial` with "Open:" where `rtc-stun` now implements and tests the clause
and `rtc-ice` or `rtc-turn` still has to adopt it; those two crates were not changed here.
Appendix B.1 and section 18.1 are read with the RFC's verified errata 6268 and 6290.

Updated again on branch `conf/turn-4-stun8489`, where `rtc-turn` adopts it: the TURN client
receives every STUN message through `Validator`, runs the long-term credential mechanism through
`LongTermCredentials`, sends on the timer of section 6.2 that it now shares with `rtc-stun`
(`rtc_stun::timer`), and offers the 300 (Try Alternate) rules to an application that follows a
redirection. The rows that still say "Open:" name `rtc-ice` only.

Conventions: Level `MUST†` is an unkeyworded procedural statement of the RFC ("the agent
checks...", "the server replies...") that an implementation has to follow; it is counted as
MUST. Sections that bind only a STUN server or the authors of other specs are one `n/a` row
each (§6.2.2 server part, §9.2.4, §10 server part, §12, §13, §17, §18), counted once. Where
components differ, the row gives the worst verdict and the note says which component does
what.

## Gaps, in order of importance

Status on branch `conf/turn-4-stun8489`: the TURN side of 1, 2, 3, 4, 6 and 9 is closed (the
rows above name the tests); what is left of 1, 2, 4 and 6 is `rtc-ice`'s.

1. **Attributes outside MESSAGE-INTEGRITY and unverified FINGERPRINT** (S). RFC8489-9-1, 9-2,
   6.3-6. One helper in `rtc-stun` that truncates `Message::attributes` at the integrity
   attribute (keeping MESSAGE-INTEGRITY-SHA256 and FINGERPRINT), applied by ICE
   (`handle_inbound`) and the TURN client (`response_is_authentic`) once the check passed; and
   a `FingerprintAttr::check` in ICE's inbound path (required-present is RFC 8445's rule).
   Fixes Bugs 1.
2. **Comprehension-required attributes** (S). RFC8489-6.3.1-1, 6.3.1.1-4, 6.3.2-1, 6.3.3-1,
   6.3.4-1. A per-usage list of known attributes; ICE answers a request with 420 +
   UNKNOWN-ATTRIBUTES, and drops indications / responses; TURN fails the transaction.
3. **RFC 8489 long-term credential features in the TURN client** (L). RFC8489-9.2.5-1, -4, -7,
   -8, -9, -13, -18, 9.2.2-1, 14.4-1, 14.6-1, 14.11-1, 18.5.1.1-1. Nonce cookie and security
   feature bits (bid-down protection), PASSWORD-ALGORITHMS / PASSWORD-ALGORITHM, SHA-256 key,
   MESSAGE-INTEGRITY-SHA256 (set and check, truncation rules), USERHASH. Needs HMAC-SHA256
   through `RTCCrypto` and a test server that speaks it.
4. **Retransmission timer** (M). RFC8489-6.2.1-1, -2, -3, -6, -7, -8, 6.2.2-2, 6.2.2-3, 6.2-2.
   One shared timer for `rtc-stun::Client` and `rtc-turn`: doubling without the 1600 ms cap,
   default RTO 500 ms, Rc and Rm configurable (7 and 16), last wait Rm x RTO, no retransmission
   and Ti = 39.5 s when the protocol is TCP, optional RFC 6298 estimate with a per-server cache,
   ten outstanding transactions per server.
5. **Error responses to unauthenticated requests** (S, needs a decision). RFC8489-9.1.3-1, -3,
   -5. ICE drops them silently (no reflection to a spoofed source); the RFC wants 400 / 401
   without integrity. Either implement behind a rate limit or record the deviation in
   `docs/conformance.md` as on purpose.
6. **Integrity failure reporting** (S). RFC8489-9.1.4-3, 9.1.4-4, 9.2.5-16, 9.2.5-17. A
   transaction whose responses were all discarded reports an integrity violation; over TCP it
   ends at once. New `Event` variant in `rtc-turn`, new pair failure reason in `rtc-ice`.
7. **Error response processing in ICE** (S). RFC8489-6.3.4-1, 6.3.4-3. Error responses are
   dropped at the top of `handle_inbound`; authenticate them, match the transaction and fail
   the check (and act on 487, which is rfc8445.md's finding too).
8. **MESSAGE-INTEGRITY-SHA256 for short-term credentials** (M, after 3). RFC8489-9.1.3-4,
   9.1.3-6, 9.1.4-1, 9.1.5-1.
9. **ALTERNATE-SERVER / 300 Try Alternate** (M). RFC8489-10-2, 10-4, 14.16-1, 6.3.4-2. Report
   the alternate address to the application (sans-I/O cannot dial) or retry inside the TURN
   client; five-minute loop guard; the anonymous Allocate must look at the error code first.
10. **Attribute limits and receive strictness** (S). RFC8489-14.3-1, 14.8-1, 14.9-1, 14.10-1,

11. **OpaqueString (RFC 8265)** (M). RFC8489-9.1.1-1, 9.2.2-1, 14.3-2. PRECIS processing of

12. **SOFTWARE** (S). RFC8489-6.1-2, 6.1-3, 6.3.1.1-6, 16.1.2-1. One optional setting applied

13. **`stuns:` with an IP address, 5xx resend, RFC 3489 compatibility** (S each). RFC8489-8.1-1,

## Bugs found

Status on branch `conf/stun-rfc8489`: 2, 3, 4, 6, 8 and 9 were confirmed with a failing test
and are fixed; 7 is fixed in `rtc-stun` (`Uri`) and open in `rtc-ice` (`Url`); for 1,
`rtc-stun` now has the API that closes it (`Validator` / `ValidatedMessage`) and the ICE agent
has to adopt it. On branch `conf/turn-4-stun8489`: 5 was confirmed with a failing test
(`client_stun8489_test.rs::test_response_of_another_method_does_not_end_the_transaction`) and
is fixed; the same class as 1 was confirmed in the TURN client (an XOR-MAPPED-ADDRESS appended
after the MESSAGE-INTEGRITY of a genuine Allocate response was handed out as the client's
address, `test_attribute_appended_after_the_integrity_of_a_response_is_not_read`) and is fixed
there.

1. **An attribute appended after MESSAGE-INTEGRITY can flip the ICE role.**
   `rtc-ice/src/agent/mod.rs:1572-1663` (`handle_role_conflict`) uses `m.contains(..)` /
   `get_from` over all attributes, and `MessageIntegrity::check`
   (`rtc-stun/src/integrity.rs:146-156`) deliberately skips whatever follows the integrity
   attribute; FINGERPRINT is not verified. Reproduction: agent is controlled; take a valid
   Binding request from the controlling peer (ICE-CONTROLLING inside the integrity), append an
   ICE-CONTROLLED attribute with tie-breaker 0 after MESSAGE-INTEGRITY, fix the header length,
   feed it to `handle_inbound`: it passes the integrity check, a 487 is sent and
   `switch_role` runs (our tie-breaker is larger), leaving both sides controlling. Same class
   as the nomination fix (`nomination_of`), which covers only USE-CANDIDATE / NOMINATION.
2. **`rtc-stun` `Client` truncates responses longer than 120 bytes.**
   `rtc-stun/src/client.rs:203-204` calls `Message::read_from`, which reads into a fixed
   `DEFAULT_RAW_CAPACITY` (120-byte) buffer (`message.rs:432-438`). Reproduction: feed
   `handle_read` a Binding success of 132 bytes (IPv6 XOR-MAPPED-ADDRESS + MAPPED-ADDRESS +
   RESPONSE-ORIGIN + a 28-byte SOFTWARE + FINGERPRINT, what coturn sends over IPv6): decode
   fails with "buffer length 120 is less than 132", the transaction retransmits and times out.
   The examples `trickle-ice` and `trickle-ice-srflx` use this client.
3. **`rtc-stun` `Client` backs off linearly and sends 8 requests.** `client.rs:50-52`
   (`(attempt + 1) * rto`) and `client.rs:270` (`attempt >= max_attempts` with 7).
   Reproduction: virtual clock, RTO 100 ms, no response: requests go out at 0, 100, 300, 600,
   1000, 1500, 2100, 2800 ms (RFC: 0, 100, 300, 700, 1500, 3100, 6300, seven in all) and the
   timeout is reported at 3600 ms (RFC: 7900 ms).
4. **`rtc-stun` `Client` accepts anything with a known transaction id as the response.**
   `client.rs:200-206` and `agent.rs:128-141`: no source address check against `remote`, no
   class check. Reproduction: start a transaction, feed `handle_read` a Binding *request* (or
   an indication) with the same id from another address: `poll_event` returns it as
   `StunEvent::Message` and the transaction ends.
5. **TURN client: a response of another method ends the transaction with no event.**
   `rtc-turn/src/client/mod.rs:377-457` deletes the transaction, then dispatches on the
   response's method; when it does not fit the transaction type (`if let ... = tr.transaction_type`
   fails, or `handle_allocate_response` hits `_ => {}`) nothing is queued, not even a timeout.
   Reproduction: `send_binding_request`, answer with an Allocate success response carrying the
   same transaction id from the server address: the Binding transaction is gone and the caller
   never gets `BindingResponse`, `BindingError` or `TransactionTimeout`. (Unsigned transactions
   only need the id; signed ones need the server.)
6. **Truncated address attributes decode to a zero-filled address.** `rtc-stun/src/addr.rs:75-84`,
   `xoraddr.rs:144-166`. Reproduction: XOR-MAPPED-ADDRESS with family 0x02 and 6 value bytes
   after the port: `get_from` returns an IPv6 address made of 6 real bytes XORed and 10 zero
   bytes, instead of an error.
7. **`Uri` / `Url` `Display` writes an unbracketed IPv6 host.** `rtc-stun/src/uri.rs:29`,
   `rtc-ice/src/url/mod.rs` (`Display`): brackets only when the host contains `::`.
   Reproduction: parse `stun:[2001:db8:1:2:3:4:5:6]:3478`, format it: `stun:2001:db8:1:2:3:4:5:6:3478`,
   which does not parse back.
8. **ERROR-CODE class is not masked.** `rtc-stun/src/error_code.rs:83`. Reproduction: an
   ERROR-CODE value `00 00 0C 26` (reserved bit set in the class byte, class 4, number 38)
   decodes as 1238 instead of 438, so a stale nonce is not recognised.
9. **USERNAME limit off by four.** `rtc-stun/src/textattrs.rs:11,65`: a 513-byte USERNAME
   builds; RFC 8489 allows at most 508 bytes (RFC 5389: 512). Reproduction: `add_to` with 513
   bytes succeeds.

Outside this spec, noticed in passing: `rtc-turn` `Client::new` resolves host names with a
blocking `to_socket_addrs` (`rtc-shared/src/util.rs:77`) inside a sans-I/O crate; ICE drops 487
(Role Conflict) error responses with every other error response (`rtc-ice/src/agent/mod.rs:1673`).

## Receive path adoption in ICE (`conf/ice-5-stun-validated`)

The ICE agent now receives requests and responses through `rtc_stun::validated::Validator`
(`rtc-ice/src/agent/mod.rs`: `handle_inbound`, `handle_inbound_request`, `ice_known_attributes`).
What that closes of the "Open: ICE" notes above (the rows keep their verdicts where TURN's
part is still open):

- 6.3-6: FINGERPRINT is verified when present, on requests and responses
  (`agent_rfc8445_test.rs::test_message_with_a_wrong_fingerprint_is_discarded`). It is not
  required: a peer's check without FINGERPRINT is still taken, as before.
- 6.3.1-1, 6.3.1.1-4 and RFC 5780 6.1-1: an authenticated request with an unknown
  comprehension-required attribute is answered 420 with UNKNOWN-ATTRIBUTES, signed
  (`agent_rfc8445_test.rs::test_request_with_an_unknown_required_attribute_is_answered_420`).
- 6.3.3-1 and 6.3.4-1: a response with such an attribute is discarded (same validator call; no
  test of its own).
- 9.1.3 / 14.5 (attributes after the integrity are ignored): the agent reads the validated

## Gaps, in order of importance

State: gaps 1 to 5 are closed (rows 6-9, 6-10, 6-11, 6-18; 6-14, 6-15; 5.1-8; 5.1-3, 6-2, 6-5,
6-12, 6-13, 7-1, 7-2). For 7-2 the decision is no cap below the negotiated stream count. No row
of this RFC is open.

1. **Close instead of error on a bad OPEN (6-9, 6-10, 6-11, 6-18), size M.** In
   `DataChannelHandler::handle_read`: (a) an OPEN on a stream that already has a channel resets
   the stream and closes that channel, with no ACK; (b) when `RTCDataChannelInternal::accept`
   fails (not DCEP, not an OPEN, unknown channel type, inconsistent lengths, invalid UTF-8) call
   the existing `reset_stream` instead of returning the error. Remove the ACK branch for
   `Message::DataChannelOpen` from `DataChannel::handle_dcep`. Four handler tests.
2. **Ordered sending until the ACK (6-15, 6-14), size S-M.** Keep the stream ordered until the
   opener has received the ACK (or any message) on the channel: either delay
   `set_reliability_params`'s unordered flag until `handshake_complete`, or add a per-stream
   "force ordered" bit that `DataChannelHandler` clears on the first inbound message. Test:
   open an unordered channel, send before the ACK, assert the DATA chunks have U = 0, then
   U = 1 after the ACK.
3. **Label length on send (5.1-8), size S.** `create_data_channel` rejects a label over 65535
   bytes, as its documentation says and as it already does for the protocol.
4. **Tests for the untested rows (5.1-3, 6-2, 6-5, 6-12, 6-13, 7-1, 7-2), size S each.**
   Reliability parameter 0 on a generated reliable OPEN; a lost OPEN / ACK on a `maxRetransmits: 0`
   channel is retransmitted; close, threshold and negotiated OPEN put no PPID 50 chunk on the
   wire; reset before ACK closes the connecting channel; reopen on a reset stream id; OPEN with
   65535-byte label and protocol; a bound (or a documented decision) on peer-opened channels.
5. **Setup failure as an error (6-12), size S.** Surface an `OnError` before `OnClose` when the
   peer resets a channel that never got its ACK.

## Bugs found

State: all four confirmed by a failing test and fixed. 1:
`an_open_on_a_stream_in_use_closes_the_channel_without_an_ack`. 2:
`a_malformed_open_resets_its_stream`, `user_data_on_a_stream_that_was_never_opened_resets_it`.
3: `data_sent_before_the_ack_is_ordered_on_an_unordered_channel` (and, between two engines,
`data_sent_before_the_ack_arrives_on_an_unordered_channel`: none of the early messages arrived).
4: `a_label_over_65535_bytes_is_refused`,
`test_channel_open_marshal_refuses_strings_over_65535_bytes`.

1. **A DATA_CHANNEL_OPEN on a stream that already carries a channel is ACKed** (6-9, 6-11).
   `rtci-datachannel/src/data_channel/mod.rs:259-264`, reached from
   `src/peer_connection/handler/datachannel.rs:253`. Reproduce: handler test; register an open
   channel on stream 4 (the helper used by `an_empty_message_counts_as_zero_bytes_received`),
   feed a well-formed OPEN with PPID 50 on stream 4, then drain `poll_write`: today a
   `DATA_CHANNEL_ACK` comes out and the channel stays open. Expected: a stream reset (the
   internal close message) and no ACK.
2. **A malformed OPEN, or user data on an unused peer-parity stream, leaves the stream
   half-open** (6-10, 6-18). `src/peer_connection/handler/datachannel.rs:275-280`. Reproduce:
   handler test as DTLS client; feed stream 1 a PPID 50 payload `[0x03, 0x7f, ...]` (reserved
   channel type), or a PPID 53 payload; today `handle_read` returns `Err` and `poll_write` is
   empty. Expected: `Ok`, with the internal close message for stream 1 queued.
3. **User data sent before the ACK on an unordered channel is sent unordered** (6-15).
   `src/peer_connection/handler/sctp.rs:803-807` with `rtci-sctp/src/association/stream.rs:565`.
   Reproduce: `SctpHandler` test in the style of `accepted_*`: write a local OPEN with
   `ReliableUnordered` on stream 0, then a PPID 53 message, flush and parse the DATA chunks
   (`wire_data`): today the user chunk has the U bit set while no ACK has been received.
   Expected: U = 0 until an inbound message arrives on the stream.
4. **A label longer than 65535 bytes produces a corrupt OPEN** (5.1-8).
   `rtci-datachannel/src/message/message_channel_open.rs:179` (`self.label.len() as u16`),
   no check in `src/peer_connection/mod.rs:2325-2354`. Reproduce: marshal a `DataChannelOpen`
   with a 65536-byte label and unmarshal it: the label length reads 0 and the protocol is
   garbage; or call `create_data_channel` with such a label and observe `Ok`.

# RFC 8446 conformance audit: the TLS 1.3 clauses DTLS 1.3 relies on

Spec: RFC 8446, August 2018, as used by RFC 9147 (DTLS 1.3): handshake, extensions, key schedule, alerts, certificate verification. One row per normative sentence (the text of the clause, cut to 25 words), plus rows marked "Implicit" for the constructions the text defines without a keyword. Rows that bind only TLS over a reliable transport (the TLS record framing, middlebox compatibility mode, EndOfEarlyData) are `n/a`; what DTLS changes is in `rfc9147.md`.

The handshake is in `rtc-dtls/src/dtls13/` (`handshake.rs`, `hello.rs`, `messages.rs`, `key_schedule.rs`); the version negotiation with DTLS 1.2 in `rtc-dtls/src/conn/mod.rs` (`negotiate_version`). Not implemented, and counted `missing`: pre-shared keys of any kind (resumption, external PSKs, 0-RTT). Not offered, so `n/a`: post-handshake authentication, OCSP and SCT, certificate_authorities, oid_filters.

## Gaps, in order of importance

1. **PSK: resumption, external PSKs, 0-RTT (L).** The `missing` rows of 2.2, 4.1.1-2, 4.1.2-12, 4.1.4-11, 4.2.9, 4.2.10, 4.2.11, 4.3.2-8, 4.6.1, 9.2-7, 9.2-8, C.4. See `rfc9147.md` gap 1 for the work.
2. **The chain's signatures at the receiver (M, owner).** RFC8446-4.4.2.3-3, -4.4.2.4-4, -4.4.2.4-5: a receiver that authenticates by fingerprint does not look at the chain's signature algorithms; that needs a decision (a fingerprint match is the authentication). The server side (4.4.2.2-5, -7) is done.
3. **oid_filters (S).** RFC8446-4.4.2.3-4: ignored when a CertificateRequest carries it.
4. **Tests for implemented rows (S each).** The `untested` rows are refusals of malformed hellos (4.1.3-4 to -6, 4.1.4-4, -5, 4.2-4, -5, -7, 4.2.8-8 to -10, 4.3.1-2, 9.2-10 to -12): each is a ClientHello or ServerHello built by hand, as `conn_conformance_test.rs` does for DTLS 1.2.

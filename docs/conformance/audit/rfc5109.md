# RFC 5109: RTP Payload Format for Generic Forward Error Correction (ULPFEC)

Spec: RFC 5109, December 2007 (Standards Track; obsoletes RFC 2733 and RFC 3009). Audited at fork master
8916bc3. Sections covered: 7, 8, 9, 11, 12, 13, 14 (all sections with requirements; 1 to 6, 10, 15 are
descriptive or examples).

**Status of the implementation.** ULPFEC is not implemented: `docs/conformance.md` decision D1 and the
"Not implemented" table of `docs/conformance/w4.md`. Nothing encodes or decodes it, the default codecs do
not offer it (`media_engine.rs:628-631`), and `MIME_TYPE_ULP_FEC` (`media_engine.rs:185`) remains so an
application with its own coder can register it. Every format and procedure clause is `missing` and
counted. The WebRTC use of ULPFEC (libwebrtc) is as a redundant encoding inside RED (section 14.2), which
also needs RFC 2198, itself missing.

What the engine does do, and is the only tested behaviour: the default offer carries no `ulpfec`
(`tests/default_codecs_omit_ulpfec.rs::default_offer_sdp_has_no_ulpfec`,
`media_engine.rs::default_codecs_do_not_offer_ulpfec`), and an explicit registration still works
(`media_engine.rs::ulpfec_remains_registerable_explicitly`).

## Gaps, in order of importance

1. **ULPFEC coder (L).** RFC5109-7.x, 8.x, 9.x: FEC header and level header writer/parser (16 and 48 bit
   masks, at least one level; multi-level protection for full conformance), encoder over a mask, decoder
   with the level-aware reconstruction. Fuzz target for the parser.
2. **RED carriage (M, depends on RFC 2198 gap 1).** RFC5109-14.2-1 to -3: the only form browsers use for
   video (`video/red` + `video/ulpfec` in the media SSRC). Interceptors analogous to the FlexFEC pair, with
   the difference that FEC shares the media SSRC and sequence space.
3. **Negotiation (S).** RFC5109-13-1, 13-4, 13-5, 14.3-3, 14.3-4: parse `onelevelonly`, tie `ulpfec` to
   `red` (drop both when the FEC payload type is not accepted), stop answering an application-registered
   `ulpfec` when no coder is bound.
4. **Separate-stream FEC (L, low value).** RFC5109-14.1-2 to -5, 14.3-1, 14.3-2, 11-2: FEC in its own RTP
   session with `a=group:FEC`. No WebRTC implementation does this and the engine has a single bundled
   transport; candidates for an explicit, permanent "not applicable to WebRTC" decision rather than work.
5. **Congestion rules (S, after 1).** RFC5109-12-1, 12-2: a FEC-rate controller that reads receiver
   reports and never raises total rate as loss rises.

## Bugs found

None: nothing is implemented, and the default SDP does not claim it. Same hazard as for RFC 8627: an
application that registers `MIME_TYPE_ULP_FEC` (the documented escape hatch) gets it offered and answered
with nothing behind it; repair packets sharing the media SSRC would then be delivered to the application
as media on the track (`handler/endpoint.rs:262-280` delivers any payload type on a known SSRC), and it
must filter them itself. Reproduction: register `video/ulpfec` on both sides, send a packet with that
payload type on the media SSRC through `write_rtp`, and observe it arrive as a `TrackPacket`.

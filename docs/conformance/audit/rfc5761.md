## Gaps, in order of importance

1. **Negotiate instead of assume (S).** RFC5761-5.1.1-3, 5.1.1-5: read the remote `a=rtcp-mux`; answer
   with it only when offered; refuse or stop a section whose answer lacks it.
2. **Payload types 64 to 95 (S).** RFC5761-4-3, 5.1.1-4: refuse them in `register_codec`, and refuse or
   ignore remote formats in that range.
3. **RTCP candidates (S).** RFC5761-5.1.3-2 (with rfc8858.md 5.3-2).
4. **Tests.** Generated offers and answers assert `a=rtcp-mux` (5.1.1-1, 5.1.1-2, 5.1.1-7).

## Bugs found

- **RFC5761-5.1.1-3:** an offer without `a=rtcp-mux` is answered with `a=rtcp-mux`
  (`src/peer_connection/sdp/mod.rs:941`). Reproduce: remote audio offer lacking the attribute; the
  answer contains it.
- **RFC5761-4-3:** a codec can be registered, or accepted from a remote offer, with payload type 72.
  Its RTP packets with the marker bit set have second octet 200 and are handled as RTCP sender reports
  by `is_rtcp` (`rtc-shared/src/util.rs:56`).

## Status after `conf/rtcp-codec` (rtc-shared)

- `is_rtcp` was checked against RFC 5761 4 and RFC 7983 and is right as it stands: it tests the whole second
  octet for 192 to 223 and does not mask the marker bit, so payload types 64 to 95 are read as RTCP only when
  sent with the marker bit, which is the collision RFC 5761 4 describes and forbids at the source. It now has
  tests over every octet value. The fix for RFC5761-4-3 is to refuse those payload types in the media engine
  (gap 2), not to change the classifier.

# RFC 6188 — The Use of AES-192 and AES-256 in Secure RTP: clause audit

Spec: RFC 6188, March 2011 (current). Audited against fork master 8916bc3; verdicts updated for branch `conf/srtp-conformance`. Scope:
`rtc-srtp/src/key_derivation.rs`, `rtc-srtp/src/cipher/cipher_aes_cm_hmac_sha1.rs`,
`rtc-srtp/src/protection_profile.rs`, profile wiring in `src/peer_connection/handler/dtls.rs` and
`rtc-dtls/src/extension/extension_use_srtp.rs`. Read-only audit; no test was run. SHALL / REQUIRED
count as MUST; RECOMMENDED as SHOULD.

Reachability: the AES-256 counter-mode suites exist in `rtc-srtp` (`Aes256CmHmacSha1_80`,
`Aes256CmHmacSha1_32`) but **cannot be negotiated by a peer connection**: the DTLS `use_srtp` enum
knows only 0x0001, 0x0002, 0x0007, 0x0008 (`extension_use_srtp.rs:28-36`) and `update_srtp_contexts`
maps only those four (`handler/dtls.rs:543-553`). RFC 6188 registers its suites for SDP Security
Descriptions only; there is no RFC-assigned DTLS-SRTP code point for them, so within WebRTC the only
consumer of this RFC is AEAD_AES_256_GCM's KDF (RFC 7714 §11). AES-192 was absent on master; the branch adds it (`rtc-crypto` and `rtc-srtp`), at crate level like AES-256.

## Open after `conf/srtp-conformance`

1. **No DTLS-SRTP code point (decision)**: 2-1, 4-1 to 4-4. The IANA "DTLS-SRTP Protection Profiles"
   registry assigns 0x0001, 0x0002, 0x0005 to 0x0010; nothing for the RFC 6188 suites (0x0003 and 0x0004
   are unassigned, and OpenSSL / libsrtp use them for AES-f8). `ProtectionProfile::dtls_srtp_id` returns
   `None` for them, so they cannot be negotiated with `use_srtp`; they are for key management that names
   the suite itself.
2. **KDF choice (S, optional)**: 3.1-5.
3. **Preference order (S, peer connection)**: 6-1.

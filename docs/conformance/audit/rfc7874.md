# RFC 7874: WebRTC Audio Codec and Processing Requirements

Spec: RFC 7874, May 2016 (Standards Track). Audited at fork master 8916bc3. Whole document covered
(sections 3 to 7).

The engine is a transport: it does not capture, encode, decode, level or echo-cancel audio. Those clauses
are `n/a`, except where the companion crate `rtc-audio` (the fork's media pipeline,
`docs/media-pipeline.md`) implements them: those rows name its code and tests. What binds the engine is which audio formats it offers, in which order, with which RTP payload
formats, and the DTMF and comfort-noise machinery, which is RTP-level.

## Gaps, in order of importance

1. **telephone-event: offered by default, with a sender (M).** RFC7874-3-7, 3-8, 3-10, 3-11, 3-13. Work
   packages 1 to 3 of `rfc4733.md`: the payload type, a sans-I/O DTMF queue enforcing 40 to 8000 ms
   durations and a 30 ms minimum gap, default registration with fmtp `0-15`.
2. **Comfort noise for G.711 / G.722 (S).** RFC7874-3-4. Work packages 1 and 2 of `rfc3389.md`: offer
   `CN/8000` (PT 13), give it a payloader and a payload type; DTX itself stays with the application.
3. **Pin the default audio offer with a test (S).** RFC7874-3-1, 3-5, 3-14: one test over
   `register_default_codecs` asserting Opus first, PCMU and PCMA present, and (once added) CN and
   telephone-event with their clock rates.
4. **Received events (S).** RFC7874-3-12: a test that an event packet is delivered with its payload type
   intact, and documentation that the application must route it away from the decoder; or an opt-in
   interceptor that parses events and delivers them as an engine event.

## Bugs found

None beyond those recorded in `rfc4733.md` (telephone-event and CN are dropped from the offer of a track that
names its codec; an unnegotiated payload type is rewritten to the media codec's) and `rfc7587.md` (audio
marker bit, echoed fmtp).

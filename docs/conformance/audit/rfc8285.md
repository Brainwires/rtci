# RFC 8285: A General Mechanism for RTP Header Extensions: clause audit

Spec: RFC 8285, October 2017 (obsoletes RFC 5285, which JSEP 5.8.2 and some code comments still cite).
The code follows RFC 8285: ids up to 255, the two-byte form and `a=extmap-allow-mixed` are present.
Audited at fork master 8916bc3. Scope: the wire format (4.1 to 4.3) against
`rtc-rtp/src/header/mod.rs`, and the SDP signalling and offer/answer rules (5 to 7) against `rtc-sdp`
and the peer connection.

Path legend: `hdr` = `rtc-rtp/src/header/mod.rs`, `extmap` = `rtc-sdp/src/extmap/mod.rs`,
`sdp/mod.rs` = `src/peer_connection/sdp/mod.rs`, `me.rs` = `src/peer_connection/configuration/media_engine.rs`,
`pc/` = `src/peer_connection/`. Tests named `packet_test::x` are in `rtc-rtp/src/packet/packet_test.rs`.

## Gaps, in order of importance

1. **Extension direction (S).** RFC8285-7-4, 7-1, 7-6: keep the offered direction, answer its reverse
   intersected with what the media engine registered for the direction, never an implicit sendrecv.
2. **Wire-format corner cases (S).** RFC8285-4.3-3 (mask the appbits: `profile & 0xFFF0 == 0x1000`),
   4.1.2-4 (stop at id 0 with a non-zero length).
3. **Validate remote mappings (S).** RFC8285-5-1 (id 15), 5-2, 5-7, 5-9, 7-9, 7-12: refuse or resolve
   duplicate ids / URIs, mixed levels, remapped ids, ids that differ across a BUNDLE group.
4. **Session-level extmap and media-level extmap-allow-mixed (S).** RFC8285-5-8, 6-6, 6-4.
5. **Extended ids 4096 to 4351 (S).** RFC8285-5-3, 7-10: at least skip them instead of failing the
   description.
6. **Enforce what was negotiated on send (M).** RFC8285-4.1.2-1, 4.1.2-6, 6-5, 4.1.2-9: check or build
   the header extensions in the sender; allow ids above 14.

## Bugs found

- **RFC8285-4.3-3:** a two-byte header extension with non-zero appbits is not parsed. Reproduce: take the
  packet of `packet_test::test_rfc_8285_two_byte_extension`, change the profile bytes `10 00` to
  `10 01`; `get_extension(1)` returns the whole block (as id 0) or nothing instead of the element.
- **RFC8285-4.1.2-4:** one-byte block `0x01 0xAA 0xBB ...` (id 0, length field 1): parsing should stop
  there; instead an extension with id 0 and two payload bytes is recorded and parsing continues
  (`rtc-rtp/src/header/mod.rs:195`).
- **RFC8285-5-3:** a remote description with `a=extmap:4096 urn:x` fails `set_remote_description`.
  rtc-sdp now parses the line (`ExtMap::parse`, `MediaDescription::extmaps`, `is_answerer_assigned`);
  what is left is in `rtp_extensions_from_media_description`, which calls `ExtMap::unmarshal` and puts
  the id it gets into RTP headers: it has to skip or remap an id that is not 1 to 255 before the
  description can be accepted. (`a=extmap:0` and ids RFC 8285 does not define stay refused.)
- **RFC8285-7-4:** an offer with `a=extmap:3/sendonly urn:ietf:params:rtp-hdrext:ssrc-audio-level` is
  answered `a=extmap:3 urn:...` (sendrecv). Reproduce with an audio offer and a media engine that
  registered audio-level.
- **RFC8285-5-8:** an offer whose `a=extmap` lines are at session level negotiates no header extension
  (`rtp_extensions_from_media_description` reads the media section only), so MID / RID routing for that
  peer silently does not work.

## Status after the RTP wire work (`conf/rtp-wire`)

The wire-format bugs are fixed: appbits (RFC8285-4.3-3), ID 0 with a length (RFC8285-4.1.2-4), and an ID above 14 set on a header without extensions (RFC8285-4.1.2-7), which the TWCC sender reached. The SDP bugs (RFC8285-5-3, RFC8285-7-4) and the enforcement of the negotiated form on send (RFC8285-4.1.2-6, 6-5) are open.

## Status after the header extension work (`conf/jsep-18-header-extensions`)

Gaps 1, 3 (except 5-9 on parse and 7-9 on a remote re-offer), 4 (media-level `extmap-allow-mixed`), 5
and 6 (except 4.1.2-1) are closed: ids to 255 with 15 never used, the negotiated `extmap-allow-mixed`
on the send path, contradicting remote mappings refused, the 4096 range remapped, directions written.
Open: RFC8285-4.1.2-1 (an application's own un-negotiated ids are passed through, by the fork's
choice) and RFC8285-5-9 (a remote description mixing session- and media-level mappings is
accepted, the section's own winning).
